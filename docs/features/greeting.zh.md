> 关联决策：域内历史决策（SSE 通道与进入问候、域更名）见文末「决策记录」；对话页集成沿[对话域·决策「统一对话式界面」](chat.md)

## 职责与边界

用户每次打开（或刷新）网页，书童主动说一句问候。

- Web 在会话历史恢复后与 server 建立一条 SSE 长连接，连接即收一句按当地时段生成的问候（AI 生成、固定文案兜底），之后仅保活。
- 问候只当次展示，不写入任何数据库。
- 2026-10-02 起同通道承载对话处理阶段的 `chat-progress` 事件：等待回复期间，等待状态行按实际行为展示（理解你的话 → 核对日程/翻账本…）。

**管**：`GET /api/v1/greeting` 事件流端点；问候生成（AI + 按时段兜底）与 30 秒去重窗口；对话处理阶段广播（chat-progress，经进度枢纽推给所有在线连接）；Web 端进入问候的连接与上屏、等待状态的真实阶段展示。

**不管**：开场播报与待办提醒等其他推送内容（远期候选，见[告示板域功能文档](todo.md)）；双向通信；问候持久化与历史回看；多用户在线状态。

## 行为契约

### 接口

`GET /api/v1/greeting?tz=<IANA 时区>`，SSE 事件流（`text/event-stream; charset=utf-8`、`Cache-Control: no-store`）；启用认证时需会话 Cookie（同源 EventSource 自动携带），未登录 401；方法不匹配 405。

| 帧或场景 | 时机 | 内容 |
| --- | --- | --- |
| `event: greeting` | 连接建立且去重窗口放行时，先于一切保活帧 | `data` 为 JSON：`{ message, generated_at, source }`，`source` ∈ `ai`/`fallback` |
| `event: chat-progress` | 对话处理推进到新阶段时（意图分类前、各域提案前、书童每个工具调用执行前） | `data` 为 JSON：`{ text }`，`text` 为展示就绪的短语（如「理解你的话」「核对日程」「翻账本」）；广播给所有在线连接，尽力而为——无连接静默丢弃、推送失败不影响对话 |
| `: ping` 注释帧 | 其后每 25 秒 | 无负载，仅维持连接；客户端不产生事件 |
| 无问候帧 | 去重窗口内的重连 | 只保活；窗口过期后新连接恢复问候（chat-progress 不去重，按事件即时广播） |

### 关键规则

- 问候**永不缺席**：未配置 AI 密钥、调用失败、超时或输出不合格（空/超过 80 字）时回退按时段固定文案；问候服务对外不抛错。
- 问候以「先生」称呼主人（2026-09-26 用户决策）：AI 提示词与兜底文案同纪律。
- 时段按用户时区计算：`tz` 查询参数（前端取浏览器 `Intl` 时区）经墙钟换算；参数缺失或非法按 UTC 兜底。
- 去重窗口 30 秒，键为会话 Cookie 令牌摘要（认证未启用时按 IP）：挡断线自动重连与开发态双挂载的重复问候；窗口过期后再次进入必再问候。
- 问候**不入库**：Web 端以本地 `greeting_` 前缀 id 追加为 assistant 消息，刷新即逝，不进 `data/chat.db`，不参与意图路由与提案。
- `chat-progress` 阶段短语由 server 在处理路径上确定性播报（不经 AI 生成）：蒸馏探测「整理这几天的对话」、意图分类「理解你的话」、各域提案「核对日程/核对账目/誊写手账/张罗告示板/记下要点」、书童应答「琢磨怎么答你」（附件路径「看你的附件」）、每个工具调用按 `TOOL_PROGRESS_PHRASES` 短语表（翻账本/翻日程/翻手账/回想记忆/看告示板，未知兜底「查资料」）。Web 收到即固定显示；事件未到或通道不可用时回退本地轮换兜底词。回复落定即清空，不持久化。
- Web 在**会话历史恢复完成后**才连接问候通道（含恢复失败路径），保证问候不被历史恢复覆盖；连接错误（含 401）静默关闭，不自动重连，会话过期由全局 401 流程接管。

### 用户路径

打开网页 → 历史恢复 → 问候连接 → 问候出现在消息流末尾 → 正常对话；关闭网页连接即断，再次进入重复上述路径。

## 安全边界

- 必须：端点在认证作用域内；去重键只存令牌 SHA-256 摘要，不存明文。
- 禁止：问候通道承载任何写入指令或数据载荷（chat-progress 只读播报，不是控制面）；绕过统一错误包络在流打开后输出错误（问候生成先于流接管）。

### 2026-09-26 · 心跳问候：SSE 长连接与进入问候

**背景**：聊天记录持久化后再进入自动恢复最近会话，但书童是"哑巴"——不会主动说话；用户提出"心跳"需求：每次进入应用主动说一句问候。此前全仓没有任何长连接实现，告示板域曾明确"Web 无推送通道"。
**取舍**：SSE 而非 WebSocket——需求是纯单向（一条问候 + 保活），浏览器原生 `EventSource` 自带重连语义，且 SSE 路由零改动即受既有 Cookie 认证守卫覆盖（WebSocket 升级请求要单独处理认证，还多一个依赖、双向能力用不上）；连接即问候、之后只保活（25 秒注释帧）；问候 AI 生成 + 按时段固定文案兜底、服务永不抛错——"一定要有"优先于"一定智能"，本地无密钥开发态也完整可用；问候不持久化——"每次进入问一次"的语义，入库会堆积且需要清理策略；30 秒去重窗口按会话身份，挡断线自动重连与开发态双挂载。被否方案：进入时普通 GET 拉取（无心跳、不为开场播报/通知推送留通道）。

### 2026-10-05 · 域更名：Heartbeat → Greeting（心跳 → 问候）

**背景**：「心跳」是传输视角的名字（SSE 长连接靠周期保活帧维系，故得名），但域实际承载的是业务——进门问候、书童人设文案、处理进度播报短语；名字与定位错位，读者被引向技术层。用户提出更名。
**取舍**：greeting 而非 presence——问候是域的主功能、中文读着自然（问候域）；presence 语义罩得更全但抽象，进度播报挂在「问候域」名下可接受（共用同一条长连接）。全量改名而非只改内部——私人应用、双端客户端同仓、无第三方消费者，API 路径 `/api/v1/heartbeat` → `/api/v1/greeting` 一次改齐最干净；SSE 事件名 `greeting`/`chat-progress` 与去重、保活等行为零变化。旧名「心跳/Heartbeat」保留在横切 ADR（历史记录不改写），完整原文见 Git 历史。
