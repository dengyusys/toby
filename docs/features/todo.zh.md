## 职责与边界

用户在对话里说一句「中午提醒我还款」「这周要把鞋子刷了」，获得一张待确认的待办提案卡（事项 + 截止日期/钟点），核对确认（或亮出 30 秒到点）后写入 `data/todo.db`。一句话里说了几件要办的事，逐件拆成多条待办进同一张卡（2026-10-06 起），不再并成一条标题。

- 勾销：说「还款这事我办好了」「还款和刷鞋都办好了」「所有待办都办完了」，获得勾销提案卡（指认一条、多条或快照全部未办），确认后相应条目翻转为 `done`（划线回看）。
- 撕掉：说「把还款那条待办删掉」「机票这条不要了」，获得撕掉提案卡（指认一条或多条），确认后物理删除。
- 回看：预览面板「告示板」标签按截止分组（逾期/今天/明天/之后/未定期），可放大全屏；已完成条目默认折叠为一行计数、点击展开划线回看（2026-10-06 用户决策，PC 与移动端同款；PC 进入批量模式自动展开——已办条目参与批量清理）。
- 批量（仅 PC 端）：面板「批量」多选模式可选任意条目（含已办）做「完成所选」「删除所选」（浏览器确认框后直写，2026-10-02 用户决策）。
- 单项直操作（仅 PC 端，2026-10-05 双端分工方向首个落地）：未办条目行首勾销键（确认框明示不可重开）、行尾撕掉键（确认框明示不可恢复），与批量同款「确认框 → 直写端点」纪律。
- 移动端为纯回看视图：批量与单项直操作都不进移动端（移动端不承载复杂操作，写入全走书童对话，2026-10-05 用户决策）。
- 书童智能体可经 `list_todos` 只读工具回答「我还有什么要办」。

**管**：`/api/todos*` 的只读列表、一句话 AI 提案（新办单条/多条、勾销与撕掉——单条、多条、全部）、确认/取消、批量直写端点（告示板按钮路径）；意图路由的 `todo` 分支（对话域第五个写入域）。

**不管**：开场播报与通知推送；待办改期、重复合并、优先级与子任务；跨待办统计；勾销条目的重开（done 不可逆回 open，不要了走撕掉）。

## 行为契约

### 数据表

`data/todo.db`（`TOBY_TODO_DB` 覆盖），首启自动建库建表：

```sql
CREATE TABLE IF NOT EXISTS todos (
  id         TEXT    PRIMARY KEY,
  title      TEXT    NOT NULL,
  note       TEXT    NOT NULL DEFAULT '',
  due_date   TEXT,
  due_time   TEXT,
  status     TEXT    NOT NULL DEFAULT 'open',
  created_at INTEGER NOT NULL
);
```

`status` 为 `open`/`done`：新办提案确认后写入 `open`，勾销提案确认后翻转为 `done`（划线回看）；撕掉（对话提案确认或告示板按钮直写）物理删除行。

### API

均为 JSON；启用认证时需会话 Cookie；错误包络沿用 server 惯例 `{ error: { code, message } }`：

| 方法与路径 | 请求 | 成功响应 | 失败 |
| --- | --- | --- | --- |
| `GET /api/todos` | — | `200 { "todos": [{ id, title, note, due_date, due_time, status, created_at }] }`（有截止按日期升序、同日无钟点在前、未定期排后） | — |
| `POST /api/todos/proposals` | `{ message, captured_at?, timezone? }`（白名单三字段） | 新办 `200 { proposal_id, expires_at, reply, action: "add", todos: [{ title, note, due_date, due_time }, …] }`（一条或多条，一句话几件事逐件拆开；条目尚未写入不带 `id`，`note` 共享同一句原话），单条 `reply` 含截止或「未定期」、多条列举标题；勾销（单条/多条）`200 { …, action: "complete", todos: [{ id, title, note, due_date, due_time }, …] }`，`reply` 单条含原截止、多条列举标题；全部勾销 `200 { …, action: "complete_all", todos: […] }`（起草时点全部未办的快照）；撕掉（单条/多条）`200 { …, action: "remove", todos: […] }`，`reply` 用「撕掉」与勾销区分；勾销/撕掉指认不出目标或板上无未办 `200 { proposal_id: null, question }`（追问，不产生提案）；主人对书童说话（建议/纠正/反馈/提问，AI 判定不是要办的事）同样返回追问（2026-10-06 起） | `400 INVALID_REQUEST`/`INVALID_TEXT`/`TEXT_TOO_LONG`；AI 故障 `503 AI_*`/`422 INVALID_AI_OUTPUT` |
| `POST /api/todos/proposals/:id/:action` | URL 参数，action 仅 `commit`/`cancel` | commit `200 { status: "committed", id }`（新办单条与单条勾销/撕掉返回 `todo_` 条目 id；新办多条、勾销多条/全部无单一归属，`id` 为 null）；cancel `200 { status: "canceled" }` | `404` 不存在或未知 action / `410` 过期 / `409 PROPOSAL_CANCELLED`、`PROPOSAL_ALREADY_COMMITTED`；提案面 GET 一律 `405` |
| `POST /api/todos/complete` | `{ ids }`（白名单单字段：非空字符串数组，去重后 ≤200） | `200 { "todos": […] }`（最新全量，与 GET 同形） | `400 INVALID_REQUEST`/`INVALID_IDS`/`IDS_TOO_MANY`；任一 id 未知 `404 TODO_NOT_FOUND`（整体回滚）；GET `405` |
| `POST /api/todos/remove` | `{ ids }`（同上） | `200 { "todos": […] }`（删除后最新全量） | 同上 |

### 关键规则

- AI 先判读「要办」「办完了」（指名某几件，还是全部）、「不要了」（2026-10-02 起，指名撕掉）还是「不是要办的事」（2026-10-06 起——主人对书童说话的建议、纠正、反馈、提问转追问，不把这句话本身当待办贴上去），输出带 `action` 字段。新办只拟标题（≤20 字行动短语）与截止；一句话里说了几件事就出几条（逐件拆开、不并成一条标题，条数上限 20），共享的日期表述适用于每件事时逐条带上；备注永远用主人原话（与手账域"不改写正文"同一纪律，多条共享同一句原话）。相对日期（今天/明天/这周五…）按 `captured_at`+`timezone` 解析；只有明确钟点或惯用时段（中午→12:00）才给 `due_time`；说不出截止输出 `null`（未定期），不猜不凑。模型偶发沿用旧的扁平单条形态时，解析层归一为一条 `items`（与记账单笔归一同一宽容纪律）。
- 新办多条（2026-10-06 起）：确认经 `addMany` 在一个 SQLite 事务内逐条写入，任一条非法整体回滚；「有钟点必有日期」的确定性清理逐条执行。
- 勾销/撕掉（单条/多条）：AI 从注入的未办清单里逐字选取目标条目 `id`（一件或多件，域内去重）；服务端确定性核对每个 `id` 真在当前未办集合内，不在则按 `INVALID_AI_OUTPUT` 拒绝（AI 只能从白名单里选，不能凭空指认）。清单为空或找不到对应条目时 AI 输出空目标，域内转为追问（不产生提案），不虚构勾销/撕掉。分界：事情办成了 → 勾销（保留划线）；事情不打算办了/条目不要了 → 撕掉（物理删除）。
- 全部勾销（`complete_all`）：服务端快照起草时点的**全部**未办条目入提案——不受注入 AI 的 10 条上下文上限影响，起草后新增的待办也不会被这次确认扫进去；空板时返回追问。确认在一个 SQLite 事务内批量翻转，任一条目异常整体回滚。
- 有钟点必有日期：AI 输出钟点而无日期时，域内确定性清理把钟点置空。
- AI 输出过本地格式与日历校验（`2026-02-30` 拒绝）后才进入提案；起草时注入最近 10 条未办清单（含条目 id）对齐命名，同样的事已在板上时新办仍出新提案（不合并），主人核对时取舍。
- 提案 TTL 10 分钟，与四域一致；commit 幂等（重复确认返回首次关联的 id，不重复写库；勾销重复翻转同样幂等）；取消是唯一拒绝方式。提案亮出 30 秒未取消即由服务端自动写入（2026-10-05 用户决策），与人工确认同一条 commit 路径。
- 批量与单项直写端点（告示板按钮路径，2026-10-02 用户决策；2026-10-05 增 PC 单项）：Web（PC 端）「批量」多选或行内单项操作 → 浏览器确认框 → `POST /api/todos/complete|remove`，沿用记忆列表删除的「显式选择 + 客户端确认框 + 直写」纪律，不经提案；两端点均在一个 SQLite 事务内逐条处理，任一 id 未知 404 整体回滚（不产生半批效果）；响应带最新全量，客户端就地刷新。撕掉不可恢复、勾销不可重开，确认框明示。移动端不调用直写端点（纯回看）。
- 意图分界：「提醒我」一次性具体事项 → todo；「以后都提醒我…」长期习惯约束 → memory；持续性按日打卡 → schedule；想法/目标/心情 → notes；汇报一次性事项已办完（含全部办完）、删掉不要了的待办 → todo。分界判例维护在意图分类器提示词。

### 异常与边界

- **未定期待办**：`due_date` 为 null 的条目排在列表末尾，提案卡与面板如实标注「未定期」，不虚构日期。
- **勾销指认不出**：板上没有对应条目（或全部勾销时板上没有未办）返回追问而非提案；AI 指认的 `id` 不在未办集合时按 `422 INVALID_AI_OUTPUT` 拒绝。重复勾销幂等（状态已是 `done` 再确认不报错）；批量勾销/撕掉在一个事务内执行，任一条目未知则整体回滚。
- **提案过期**：TTL 过后 commit/cancel 返回 `410 PROPOSAL_EXPIRED`；Web 剩余秒数归零后禁用确认按钮。
- **并发**：内存提案存储单进程语义，server 是唯一写入进程；确认写库经 SQLite 同步事务串行化。
- **权限**：所有 `/api/todos*` 在认证作用域内，未登录由全局 auth guard 返回 401。
- **空库**：`todos` 返回空数组，Web 显示空态文案并引导去对话里说「提醒我…」。

## 安全边界

AI 只产出待办内容字段（标题/截止日期/截止钟点）与未办清单内的条目 `id`（勾销/撕掉目标只能从注入的白名单里选，全部勾销只输出动作标记、目标集合由服务端快照决定，服务端复核），不接触库路径与写入能力；对话提案的确认/取消只交 `proposal_id`（URL 路径），不提交标题、日期或任何超出契约的字段；批量直写端点只交用户在告示板上显式选择的条目 `ids`（按钮路径，记忆列表删除同款纪律——「显式选择 + 客户端确认框 + 直写」）；`data/todo.db` 仅 server 写入。

## 验收

自动化已通过（存储含单条/批量勾销翻转、批量撕掉回滚与 `addMany` 多条事务写入、提案服务含新办单条/多条与勾销/撕掉各形态路径单测、HTTP 集成新办单条/多条/勾销/撕掉全链路及追问形态、直写端点契约边界与 405 面、意图枚举、Web 提案卡含新办多条（条数标题、共享原话一次、逐条截止）与历史单条兼容、勾销/撕掉形态及看板批量模式交互（选择/确认框/直写/刷新清选/空板无入口），见测试）；真实 AI 盲测（「中午提醒我还款」→ 提案卡 → 确认 → 面板回看；「明天要买猫粮、买米」→ 一张多条新办卡 → 确认 → 面板两条回看；「还款这事我办好了」「还款和刷鞋都办好了」「所有待办都办完了」→ 勾销卡 → 确认 → 划线回看；「把还款那条待办删掉」→ 撕掉卡 → 确认 → 条目消失；面板「批量」勾选 → 完成所选/删除所选）待用户复核。

## 决策记录

本域历史决策的背景与取舍。只追加、不改写；实施细节以代码与测试为准，完整原文见 Git 历史。

### 2026-09-20 · 告示板域最小版（后续三次修订）

**背景**：用户说「中午提醒我还款」，收到的是书童智能体用纯文本"起草"的假提案——没有确认按钮。根因：一次性、有截止的待办在四域（日程打卡/记账/记忆/手账）里都装不下，意图分类器没有可路由的归宿；《书童的字条》底稿早已规划"告示板"域（待办/备忘，一次性、有截止、有完成态），判例表把「我这周要把鞋子刷了」裁决给告示板。
**取舍**：独立 `todo.db` 与第五个意图/提案域——待办的消费方式是查询与翻转状态，按底稿总原则归 SQL，与日程 tracker"记录发生了什么"的模型分立；提案生命周期照抄既有域——统一信封、隐式确认、提案卡"确认即看"全部自动获得，边际成本最低；AI 只拟标题与截止、备注永远用主人原话（与手账"不改写原话"同纪律），截止解析失败落为未定期而非拒绝，避免一句话被卡死。**后续演进**：09-26 完成态勾销（AI 从注入的未办清单指认条目，一条/多条/快照全部）；10-02 撕字条（`remove` 提案，与勾销同一指认纪律）与面板批量直写（「显式选择 + 确认框 + 直写」纪律，本域第一条非提案写入路径，与记忆列表删除同款例外）；10-05 双端分叉——PC 端加单项勾销/撕掉直操作、移动端撤批量变纯回看（双端分工方向首个落地，见 ADR「Web 拆分双应用」修订记录）。

### 2026-10-06 · 一句话多条新办

**背景**：用户说「明天要去买猫粮，明天要去买米，明天要去换四件套，明天要去搞卫生」，四件事被并成一条标题「买猫粮、买米、换四件套、搞卫生」写入；追问「你应该拆分成几个代办」、重发「添加若干待办：1. … 4. …」仍是一张单条卡——用户反馈不支持一次建多条（对话实测，2026-10-06）。
**取舍**：新办协议从单条改为条目数组——AI 输出 `items`（几件事逐件拆开、各自解析截止、共享日期逐条带上、上限 20 条），提案载荷 `entries` 数组，确认经 `addMany` 单事务批量写入（任一条非法整体回滚），响应与提案卡统一为 `todos` 数组（与勾销/撕掉同形；新办条目尚未写入不带 `id`，多条 commit 无单一归属 `id` 为 null，与勾销多条一致）；模型偶发沿用旧扁平单条形态时解析层归一（与记账单笔归一同一宽容纪律），Web 历史消息按旧单条 `todo` 兼容渲染（与记账 `transactions` 迁移同款）。被否方案：前端把合并标题再拆开——标题一旦并成就丢了各件的截止信息，拆不回来；限制一次只说一件事——一句话说几件事是常态，强拆发送次数是倒退。

### 2026-10-06 · 「不是要办的事」转追问（问题三 b）

**背景**：用户说「你应该拆分成几个代办」，todo AI 的规则是「其余的待办请求都按 add 处理」，这句对书童说的话被原样当待办贴上告示板（标题：把这条待办拆分成几条待办，后手动取消）。根因：判读协议只有 add/complete/remove 三种动作，没有「这句话根本不是在说一件要办的事」的出口。
**取舍**：协议补第四种形态 `{"action": "none", "question": …}`——AI 识别主人对书童说话（建议、纠正、反馈、提问）时输出一句追问，服务层转 `{ proposal_id: null, question }`，不出提案不落库（与勾销/撕掉指认不出目标的追问路径同出口）；分界写进提示词：主人陈述一件要办/办完了/不要了的事 → 对应动作；评价、指挥或质问书童 → none。与意图分类器同日新增的 2d/2e 判例（「记一下」+要办/要修的问题 → todo；纠正上一轮按纠正后的域折叠重路由）构成问题的完整闭环。被否方案：给 todo 域做真正的「拆分」动作——多条新办落地后拆分场景基本消失，为已消失的场景加协议分支不值。
