# 对话域（Chat）：统一对话界面

[English](chat.md) | 简体中文

> 目标契约(域未实施):职责、契约、边界与验收;实现以代码与测试为准。
> 关联决策：域内历史决策（统一对话界面、只读工具 Agent、书童附件、语境式预览入口）见文末「决策记录」；todo 意图分界见[告示板域功能文档](todo.md)

## 职责与边界

Web 全应用只有一个对话框。用户输入任意一句话，系统自动判定意图（日程/记账/记忆/手账/待办/none），生成对应提案、追问、说明性回复（如记忆域无可执行动作时把 AI 说明作正文，2026-10-06）或书童式回应，全程多轮可用。

- 对话历史服务端持久化，刷新页面后可恢复。
- 书童只有一个持续对话——界面恢复最近会话，不提供会话切换/新建/删除（服务端会话 API 保留用于找回这一个对话）。
- 各域的浏览能力不回退：按需预览面板（日程/记账/记忆/手账/告示板五面板）+ 全屏查看层（复用各域视图，含月历键盘导航；告示板与记忆在 PC 端含直接操作，见对应功能文档）。
- 移动端另有左侧导航抽屉（2026-10-05，决策「语境式预览入口」修订）与三页滑动分页（手账 | 对话 | 告示板）：前者是六域统一入口（预览组三项唤起底部抽屉），后两者是手账/告示板的常驻页入口。

**管**：

- `/api/v1/chat/*` 的消息发送（意图路由分发）、会话管理、消息查询、卡片终态记录。
- `data/chat.db` 会话与消息持久化。
- 附件（决策「书童附件」）：`/api/v1/attachments*` 上传与取件、`data/attachments/` 文件本体与 chat.db 元数据。

**不管**：

- 服务端对话 TTL 清理策略。
- 记账结构化录入 Web 表单（端点保留供程序化调用与测试）。
- 记录修改/删除、预算报表、多用户。
- 外部世界查询（天气、汇率等；将来登记新工具接入，见 决策「书童只读工具 Agent」远期问题）。

**不变**：既有提案管线（生成/确认/取消）路径、动作、状态码、响应结构零改动——对话域只做意图路由与消息留存。

## 行为契约

### 接口

除附件上传（multipart/form-data，决策「书童附件」对"只收 JSON"的唯一破例）外均为 JSON；启用认证时需会话 Cookie；错误包络 `{ error: { code, message } }`：

| 方法与路径 | 请求 | 成功响应 | 失败 |
| --- | --- | --- | --- |
| `POST /api/v1/chat/messages` | `{ text, captured_at, timezone, session_id?, attachments? }`（键白名单，多余键 400；`attachments` 为 1–3 个附件 id，带附件时 `text` 允许为空） | `200 { session_id, message: 统一消息信封 }` | `400 INVALID_REQUEST/INVALID_TEXT/TEXT_TOO_LONG/INVALID_CAPTURED_AT/INVALID_TIMEZONE/INVALID_ATTACHMENTS`（数量超限/重复/不存在/已被引用）；`404 SESSION_NOT_FOUND`；AI 故障 `503 AI_NOT_CONFIGURED/AI_UNAVAILABLE/AI_RATE_LIMITED`、`504 AI_TIMEOUT`、`422 INVALID_PARSER_OUTPUT`；`429 RATE_LIMITED`（含 `Retry-After`） |
| `POST /api/v1/attachments` | multipart/form-data 单文件（jpeg/png/webp/gif ≤10MB；pdf/docx/txt/md/epub/mobi ≤20MB） | `200 { attachment: { id, kind: "image" \| "document", name, mime, size_bytes, url } }`（文档同步抽取文本缓存） | `400 INVALID_REQUEST`（multipart 缺文件）；`415 UNSUPPORTED_MEDIA_TYPE`（白名单外/非 multipart）；`413 PAYLOAD_TOO_LARGE` |
| `GET /api/v1/attachments/:id` | — | `200` 原始字节（图片 inline、文档 `Content-Disposition: attachment` 按原名；`Cache-Control: immutable`——id 内容寻址的 no-store 例外） | `404 ATTACHMENT_NOT_FOUND` |
| `GET /api/v1/chat/sessions` | — | `200 { sessions: [{ id, title, updated_at, message_count }] }` 倒序 | — |
| `POST /api/v1/chat/sessions` | 空对象 | `200 { session: { id, title, created_at, updated_at } }` | — |
| `GET /api/v1/chat/sessions/:id/messages?limit=&before=` | limit 可选（1–500，默认 100）；`before` 可选游标（已加载的最旧消息 id，取其之前更早的一页，供"加载更早"向上翻页；未知 id 返回空页） | `200 { session_id, messages: ChatMessage[] }` 升序（页内），`has_more: boolean` 标记是否还有更早消息 | `400 INVALID_LIMIT`；`400 INVALID_BEFORE`（空串）；`404 SESSION_NOT_FOUND` |
| `DELETE /api/v1/chat/sessions/:id` | — | `200 { status: "deleted", session_id }` | `404 SESSION_NOT_FOUND` |
| `POST /api/v1/chat/messages/:id/outcome` | `{ status: "committed" \| "canceled" }` | `200 { status: "ok", message_id }` | `400 INVALID_REQUEST`；`404 MESSAGE_NOT_FOUND`；无提案的消息 `409 MESSAGE_HAS_NO_PROPOSAL` |

`POST /api/v1/chat/messages` 限流 20 次/60 秒/IP（与 commands/text 同窗口）；会话管理端点不限流。

统一消息信封（成功响应的 `message` 字段）：

```jsonc
{
  "id": "msg_…", "role": "assistant", "content": "回复文案",
  "intent": "schedule | ledger | memory | notes | todo | none",
  "questions": ["…"],            // 可空：schedule questions[] / ledger question 归一
  "proposal": {                   // 可空
    "kind": "schedule | ledger | memory | notes | todo",
    "proposal_id": "…", "expires_at": "ISO-8601",
    "payload": { /* 域原响应负载：schedule {summary, changes, requires_month_create}；ledger {transactions}；memory {actions}；notes {entry, append_to, rewrite, remove, merge, new_topic, topic_append}（无标题化后 entry 为 {date, body}，目标指认统一为正文摘录，见 手账决策「手账操作框架」修订记录；new_topic/topic_append 为 {name, body}——主题本开新/点名续写，见 手账决策「手账双轨存储」；不携带的操作字段为 null）；todo {action, todo|todos} */ }
  },
  "outcome": null,
  "attachments": [                 // 可空（决策「书童附件」）：用户消息携带的附件引用
    { "id": "att_…", "kind": "image | document", "name": "…", "mime": "…", "size_bytes": 0, "url": "/api/v1/attachments/att_…" }
  ],
  "inspect": [                     // 可空（决策「语境式预览入口」）：书童应答的查看芯片
    { "panel": "calendar | ledger | memory | notes | todo", "month": "YYYY-MM | null" }
  ],
  "created_at": "ISO-8601"
}
```

### 关键规则

**意图分类**：

- 输入为用户文本 + 最近上下文，输出 `{ intent, self_contained_text }`（把追问碎片折叠成自足句子）。
- 机制（决策「自管 AI JSON 协议」）：分类输出走 json_object 文本 + 本地枚举与长度校验，不依赖端点的原生工具调用解析；解析失败自动重试一次，仍失败落库**诚实重发提示**（"我刚才没听清你这句话，麻烦再说一遍。"——不 5xx、不静默丢写入，2026-10-05 用户决策）；传输类错误（超时/限流/未配置）照常报错信封。
- 意图为 `schedule` / `ledger` / `memory` / `notes` / `todo` 时分发给对应提案服务（复用既有生成管线与确定性校验）。
- 意图为 `none` 时交给书童智能体应答（决策「书童只读工具 Agent」：带只读工具的 Agent）——AI 自主决定调用工具（最多 3 轮，每轮输出一个 JSON：批量要数据 `{"calls":[…]}` 或直接作答 `{"answer":…}`，决策「自管 AI JSON 协议」），据实回答账本/作息/记忆/手账/待办的自家数据，只用真数据、不编造，超长列表如实说明截断；闲聊与知识类问题零工具调用直接回答；失败回退固定文案、不向用户报错。
- 五域分界判例维护在意图分类器提示词（todo 与 schedule/memory 的边界见[告示板域功能文档](todo.md)）。

**写入触发**（2026-09-16 用户决策「统一对话式界面」立显式确认与默许；2026-10-05 追加 30 秒自动写入）：

- **显式确认**：「确认写入」按钮，调对应域既有 commit 端点（只用 `proposal_id`）。
- **下一条消息默许**：发送下一条消息即视为接受此前所有待确认提案。Web 在发送前把待确认提案逐条（旧到新）提交到对应域既有 commit 端点；任一失败（过期/冲突）不阻塞新消息、仅提示。
- **30 秒自动写入**：提案亮出 30 秒未取消，server 到点自动提交——与人工确认同一条 commit 路径，幂等；已取消/已过期/冲突由各域状态机裁决，只留服务端日志，不影响进程。前端不感知：已自动写入的卡片仍显示按钮，再点确认幂等成功、点取消提示「已提交」，刷新后见最新数据。
- 「取消」是唯一拒绝路径，须在自动写入（30 秒）之前点击。server 对消息默许不感知（无新端点、无契约变更）；30 秒计时在 server 内（`proposal-lifecycle` 内核与日程提案服务）。

**消息与容错**：

- `outcome` 是展示元数据：仅影响历史卡片的终态渲染，不影响任何业务数据；客户端在调既有 commit/cancel 成功后上报。
- 用户消息先持久化再调分类器。AI 故障时本轮 user 消息已落库、assistant 消息不产生、不产生提案，客户端保留输入文本可重试。
- AI 结构化输出带三层防护：JSON 模式、宽容提取（剥围栏 + 最外层对象兜底）、解析失败自动重试一次（2026-09-28「AI 返回的不是有效 JSON」事故后的加固，最终失败才 422，对外错误语义不变；决策「自管 AI JSON 协议」后手账/告示板/记账/意图分类/日程指令解析统一走内核 `json()` 单一入口）。
- Web 发送即乐观上屏用户气泡并清空输入框；等待期间显示思考状态；回复到达追加 assistant 消息，失败撤回气泡并回填原文。

**提案卡呈现**（2026-09-28 修订，用户决策：裸文字行改卡片容器）：

- 日程：分组字段行「字段 旧值 → 新值」（保留未记录/是·否/数值区分）与 TTL。
- 记账：逐笔多行，多笔带合计行。
- 记忆：动作行。
- 手账：类型/标题/落页行（续写标明补充到哪条；改写为「旧值 → 新值」对比行，[手账域·决策「手账操作框架」](notes.md)）。
- 待办：事项/截止行。截止/落页等元信息读作卡内数据；行内小按钮确认/取消。

**附件**（决策「书童附件」）：

- 两段式：先 `POST /api/v1/attachments` 落文件拿 id，发消息时 JSON 引用。
- 带附件的消息**不进意图分类**，一律交书童智能体应答（附件参与提案是远期）。
- 理解分轨：文档由 server 抽取文本（上传时缓存、复用不重抽）注入现有文本模型；图片按 `TOBY_AI_VISION_MODEL` 角色覆写走视觉模型（ADR「统一 Responses API」），当轮注入原图，历史轮只留文字回应。未配置或不可用时降级——图照收照存、回复如实说明看不到图，不向用户报错。
- 文档抽取文本注入共享 3 万字符预算，超长截断注明。
- 附件一次性（一个 id 只能随一条消息）；孤儿附件（上传后 24 小时未发送）由 server 启动时清理。

**查看芯片**（决策「语境式预览入口」）：

- 书童应答过程中实际调用的只读工具确定性映射为 `inspect` 芯片（五域全覆盖，月型工具带月份；AI 不参与标注，同面板保留最后一次月份）。Web 点击芯片直达对应预览面板并定位月份。
- 预览面板的语境式唤起不变：查看芯片与已确认提案的「查看」直达面板。抽屉为**单面板形态**（2026-09-28 修订：tab 栏退役，标题随面板，想看别的回对话再说一句）。
- 移动端为**左侧导航抽屉 + 三页滑动分页**形态（2026-10-05 修订；分页本身是 2026-09-28 决策）：左上角汉堡键唤起左滑导航，六项与桌面活动栏同清单——「页面」组（手账/对话/告示板）切分页常驻页（原生 scroll-snap、三页保活），「预览」组（日程/账单/记忆）唤起底部抽屉，兼作这三域的第一个常驻入口。手账/告示板的芯片与「查看」直达改为切页（手账芯片仍带月份定位），日程/账本/记忆的芯片行为不变；桌面形态不变。
- PC 端在**窄屏（<768px，手机上打开 `/`）为补充形态**（2026-10-05 修订，决策「桌面活动栏外壳」）：活动栏不驻留，顶栏左上角汉堡键唤起左滑浮层导航（z-50 覆盖主体，六项同清单同高亮），主体占满全宽；桌面形态（≥768px）不变。

### 异常与边界

- **追问碎片**：用户对追问的补充经分类器折叠为自足句子后再分发；折叠结果仍要过对应域确定性校验，不豁免。对上一轮的**纠正指令**（「这个应该添加到待办，而不是记忆」）同样经分类器按纠正后的目标域分类并折叠被指代内容（判例 2e，2026-10-06）；被指代内容不明确时回 none 交书童回应。
- **提案过期/冲突**：消息内卡片倒计时归零禁用确认；`410/409` 错误在卡片上就地提示"请重新生成"，对话流保留原卡片为终态快照。隐式确认只处理仍处有效期的待确认提案。服务端 30 秒自动写入后的卡片可能仍显示按钮（再点幂等成功，见「写入触发」）。
- **进程重启**：内存提案存储丢失，历史消息凭 `proposal_snapshot` 仍可渲染卡片（只读终态，无确认按钮）；`data/chat.db` 不受影响。
- **删除会话**：SQLite 事务级联删除消息；正在进行的 pending 提案不受影响（提案域独立），仅对话记录消失。
- **隐私**：对话内容属于个人数据，落 `data/chat.db`（Git 忽略），启用认证时全部端点在认证作用域内；记忆域的敏感内容策略不适用于对话留存——对话原文即用户输入，删除权靠删除会话。附件同边界：文件落 `data/attachments/`（Git 忽略），取件端点在认证作用域内；日志不落附件内容与抽取文本。
- **扫描件/加密件**：文档抽取为空（无文字层）不失败——附件照存，书童应答如实告知"没有可读文字层"；真正读懂扫描件需视觉模型（看图路线），不单做 OCR。
- **端点泄漏事故**（决策「自管 AI JSON 协议」）：历史消息若含端点泄漏的内部标记（DSML 族），喂 AI 前替换为占位符；书童出口校验拦含泄漏标记的回答（回退固定文案）；chat.db 原文永不改写。
- 会话与消息不含用户维度（单用户本地数据，同 memory/ledger 惯例）。

## 安全边界

- 必须：chat 域不直接写任何业务数据，只写自己的 chat.db；对三条提案管线的调用全部经端口注入（`domains/chat/ports.ts` 声明、装配层包装），chat 域文件不 import 其他业务域。
- 必须：书童智能体（none 路径应答）的工具全部只读——账本/作息/记忆的确定性读函数，构造上无写入能力；写入意图在意图分类处已被分流进提案管线，进不到 Agent。
- 限制（决策「书童只读工具 Agent」数值，「自管 AI JSON 协议」改机制、数值不变）：工具循环 ≤3 轮（末轮指令强制 answer 作答）；单轮批量调用 1~4 个；单次工具结果回填 ≤6000 字、单轮合计 ≤12000 字；列表类工具 ≤50 条，超出截断并附 `truncated`/`total` 标记；输出校验（非空、≤800 字、不含泄漏标记）非法或 AI 不可用回退固定文案、绝不 5xx；喂 AI 前把带泄漏标记的历史消息替换为占位符（chat.db 原文不动）。
- 禁止：提案端点契约变更——对话域对既有生成/确认/取消端点零改动，客户端不提交 operations、文件路径或超出契约的数据。
- 附件（决策「书童附件」）："请求体只收 JSON"的破例仅限 `POST /api/v1/attachments`（multipart 流式解析，大小在端点层硬限）；存储文件名由服务端生成（扩展名白名单映射），客户端不提交路径；只有 server 写 `data/attachments/`；格式白名单 jpeg/png/webp/gif 与 pdf/docx/txt/md/epub/mobi 之外一律 415；文档抽取经一次性 Python 子进程（packages/text-extraction，ADR「文档处理引入 Python 运行时」），失败降级为无文字层、不阻塞上传。

## 验收

- 自动化（已通过，见 `apps/server/test/` 域与单元测试、根 HTTP 集成测试与 `apps/web/test/` 渲染测试）：意图分发与书童智能体应答（工具集输出预算与截断标记、循环末轮收工具、capturedAt/timezone 透传、失败回退）、会话管理、消息校验、六端点 HTTP 契约、限流第 21 次 429、隐式确认先于新消息、旧 hash 重定向、三类提案按 kind 紧凑渲染、挂载恢复最近会话；全部使用临时数据目录，不调用真实 AI。
- 既有提案端点契约零改动：根 HTTP 集成测试原样通过。
- 附件（决策「书童附件」，已通过）：两段式全链路集成（上传→引用→书童应答→历史塑形→认证取件、附件一次性）、上传边界（415/413/缺文件）、消息侧校验；文档抽取经真实 Python 子进程（txt/md 直读、GBK 编码探测、手工构造的合法 pdf、stored-zip docx 与 epub 夹具、mobi 与坏文件容错、解释器缺失降级，ADR「文档处理引入 Python 运行时」）；附件存储登记/认领/TTL 清理；Web composer 粘贴上传、待发预览、发送携带 id、气泡缩略图与文件卡。

## 决策记录

本域历史决策的背景与取舍。只追加、不改写；实施细节以代码与测试为准，完整原文见 Git 历史。

### 2026-09-16 · 统一对话式界面

**背景**：原交互是"三 Tab + 三套表单"——是"对语句做 AI 处理的表单"而非"吩咐书童"的对话感，三个入口迫使表达前先选域；server 侧无会话概念，三条提案管线都是单次请求/响应，没有多轮上下文与历史留存。
**取舍**：意图路由放服务端（一句话归哪个域只有 AI 能可靠判定，且服务端才能携带最近上下文把追问碎片折叠成自足句）；新建 chat 域而非并入 proposals（会话/消息/意图模型与提案模型正交，跨域调用经端口注入保住单向依赖）；独立 `chat.db`（对话的生命周期与保护级别不同于事实数据）；提案展示快照随消息入库（提案是内存对象，历史消息须自带渲染快照）；浏览能力不删只降级为按需面板 + 全屏层（铁律"只读月历不可坏"）。被否方案：纯前端编排（意图判断不可靠、无多轮上下文）、localStorage 存史（与设备绑定）、在既有提案端点上叠 session（污染冻结契约）。同日修订：确认语义扩为双路径——显式确认或**发下一条消息的隐式确认**，「取消」是唯一拒绝；次日 none 路径升级为书童式回应（闲聊兜底、失败回退固定文案）。

### 2026-09-18 · 书童只读工具 Agent

**背景**：统一对话页落地后书童会"记"不会"答"——none 路径只有闲聊，问"这个月花了多少"答不了实事；三域数据在库、确定性只读函数现成，只是对话路径取不到。
**取舍**：Agent 而非 workflow——大脑是 AI、手脚是工具，新增能力 = 往工具清单登记一项，不写固定流程（防 workflow 回潮）；走 none 路径、不新增 query 意图（零契约改动；写入守门在分类器、应答大脑在 Agent，两级分离）；权限模型刻意与 bash 型 agent 相反——工具构造上只读，写入意图在意图分类处已被分流进提案管线，物理上进不到 Agent；循环与输出纪律（≤3 轮末轮收走工具强制作答、工具失败返回数据形态不抛异常、列表 ≤50 条带截断标记、单次回填 ≤6000 字、输出 ≤800 字）借鉴 pi 的工程实践，取其成本与终止性纪律、弃其万能工具面。

### 2026-09-27 · 书童附件（图片与文档）

**背景**：用户要"主人随手把材料递给书童——照片看一眼、文件读一遍、东西都收好"；当时零基础（请求体只收 JSON、无附件存储位置、无上传入口），DeepSeek 4.1 系模型支持视觉，看图无需新增供应商。
**取舍**：两段式上传——multipart 破例仅限附件上传端点，发消息仍是 JSON 引用 id（粘贴即传、重发不重传、消息契约不变）；被否的消息端点混合 multipart 有部分成功难处理的retry语义。元数据进 `chat.db`（附件与消息共生灭、量级小，少维护一个库）；理解分轨——文档由 server 抽取文本走文本模型、图片按角色覆写走视觉模型，两条线落地互不阻塞；原图仅当轮注入（视觉 token 贵，书童文字回应已承载图的记忆）；扫描件/加密件如实说明"没有可读文字层"，不单做 OCR（真读懂扫描件归看图路线）。

### 2026-09-27 · 语境式预览入口（查看芯片）

**背景**：预览面板作为"按钮打开的弹窗"信息输出价值低——打开成本高而获得信息少；书童智能体本就能用只读工具回答"这个月花了多少"这类问题。
**取舍**：预览结合语境——书童应答实际调用了哪些只读工具，就在回答消息上给可点击的查看芯片，常驻按钮入口彻底删除；芯片由工具调用**确定性推导**（AI 不参与标注：芯片是交互入口，缺失或指错直接伤害信任，工具调用记录是系统事实、零幻觉）；常驻入口与语境入口并存会回到"随时可开的弹窗"旧习，用户选单一心智。被否方案：AI 自标注（漏标/错标）、保留常驻按钮兜底、客户端关键词识别（脆且错位）。入口形态后续演化：预览抽屉收敛单面板（09-28）、移动端三页分页（09-28）、桌面活动栏外壳（09-30，见 ADR「桌面活动栏外壳」）、移动端左侧导航抽屉（10-05）。

### 2026-10-05 · 自管 AI JSON 协议（工具调用机制换轨）

**背景**：真实使用中书童把端点泄漏的内部调用标记（DSML）当正文回复给了主人——端点的服务端解析器没把模型的工具调用转成结构化数据，且泄漏块里模型还幻觉了不存在的工具名；意图分类走同一解析器，泄漏落在它头上用户连回复都收不到。
**取舍**：见 ADR《AI 链路自管 JSON 协议》（横切决策，涉及五域 AI 客户端与传输内核）。对话域要点：书童工具循环弃端点原生 function_call，改每轮一个 JSON（`calls` 批量 1~4 / `answer` 二选一）本地解析执行，末轮指令强制 answer；意图分类弃 strict 封套改 json_object 文本，解析失败（重试一次后）落库诚实重发提示（用户决策：不 5xx、不静默丢写入）；出口三查拦泄漏标记、喂 AI 前清洗带标记的历史（库内原文不动）。被否方案：检测泄漏兜底（治标）、退回 chat.completions（仍押服务端解析器，留作盲测失败退路）、解析 DSML（绑死供应商内部格式）。

### 2026-10-05 · 提案亮出 30 秒自动写入（写入触发三路）

**背景**：默许窗口是「到下一条消息为止」——主人发完一句就离开屏幕时，待确认提案会一直挂着直到 10 分钟 TTL 过期作废，想记的事反而没记上；用户提出把沉默本身也当作认可。
**取舍**：写入触发定为三路——显式确认、下一条消息默许（均沿用既有端点与前端行为）、**亮出 30 秒未取消即服务端自动提交**；计时放 server（`proposal-lifecycle` 内核 `armAutoCommit` 回接 + 日程提案服务同款计时，`unref` 不拖进程退出，失败只留 warn）而非前端——关掉页面也如实写入，且 commands API 直连生成的提案同样覆盖；自动提交走与人工确认完全相同的 commit 路径（幂等、冲突检测、事务回滚都不豁免），已取消/已过期由状态机裁决而非计时器特判。取消窗口相应从「下一条消息前」缩短为 30 秒内。被否方案：前端倒计时（关页即失效、双端两套逻辑）、30 秒到点作废（方向相反——把默许换成超时拒绝，与需求不符）。

### 2026-10-06 · 附件文档抽取转 Python 运行时

**背景**：Node 抽取（mammoth/unpdf）解不了 GBK 编码的中文 txt（乱码），也接不动后续小说功能要的 epub/mobi（Node 无像样的 mobi 库）；用户决策静态文档处理统一转 Python 公共包、server 子进程调用，chat 附件一并切换。
**取舍**：机制换代、契约不动——`POST /api/v1/attachments` 的请求/响应/错误码逐字不变，白名单顺带扩到 epub/mobi（文档类 20MB 上限不变）；抽取器从域内纯模块（`attachment-extraction.ts` 退役）改为装配注入的基础设施内核（`infrastructure/text-extraction/`），失败语义沿用「返回 null 不抛错、附件照存、书童如实告知无文字层」，新增的失败形态（子进程超时/崩溃/venv 缺失）并入同一条降级路。完整取舍见 ADR《文档处理引入 Python 运行时》。被否方案：全 Node（mobi 缺库）、常驻 Python worker（单用户低频，简单性优先）。
