# 日程域（Schedule）

[English](schedule.md) | 简体中文

> 目标契约(域未实施):职责、契约、边界与验收;实现以代码与测试为准。
> 关联决策：ADR「日常日程操作统一经过 server」；ADR「日程记录项完全用户自定义」；域内历史决策（数据源选型、记录项化、抽取规则归属、迁移基线）见文末「决策记录」

## 职责与边界

把自然语言转换为受限、可验证的日程修改提案；显示每个目标字段的日期、记录项、旧值和新值；经用户核对确认才写入日程数据（显式确认、下一条消息默许或亮出 30 秒到点，三者任一）。

- 日程内容由**记录项（tracker）**承载：系统不预装任何记录项、不设内置分类——要记什么由用户经对话创建（提案制），全部记录项同模型、同链路。
- 记录项定义（名称、字段、枚举）是数据：新增、归档、调整字段都不需要改代码。

**管**：

- 记录项定义的创建、归档与字段调整（提案制）。
- 全部记录项的只读月份/记录/定义 API 和提案生成、确认、取消 API。
- AI 结构化解析（schema 由活跃记录项定义动态生成；无活跃项时 operations 为空集，创建记录项是唯一写入路径）、歧义追问、字段校验。
- 冲突检测、串行提交、月份创建、SQLite 事务回滚和幂等确认。

**不管**：AI 直接读写日程数据、访问数据库路径或执行 Shell；绕过提案流程的任何自动提交（亮出 30 秒的到点写入走提案 commit 路径，不在其列）；离线写入队列、用户操作历史和撤销；删除整个日期记录；记录项改名/改 slug、改字段类型、删字段或历史数据（amend 只能加字段与停用字段）；多选枚举/计数器/等级字段类型；频率与期限规则引擎；记录项间联动与跨项统计（查询能力归书童智能体）。

## 行为契约

### 接口与兼容承诺

以下表格定义公共 API 的兼容承诺。server 实现路由，Web 在自身 API client 中维护消费路径，根 HTTP 集成测试验证两者一致：

| 操作 | 路径 | 客户端输入 |
| --- | --- | --- |
| 月份列表 | `GET /api/months` | 无 |
| 记录项定义 | `GET /api/trackers` | 无（返回全部含已归档，按创建先后） |
| 月份记录 | `GET /api/records?month=YYYY-MM` | 月份查询参数 |
| 生成提案 | `POST /api/v1/commands/text` | `{ text, captured_at, timezone }` |
| 确认提案 | `POST /api/v1/proposals/{proposal_id}/commit` | 空请求体 |
| 取消提案 | `POST /api/v1/proposals/{proposal_id}/cancel` | 空请求体 |

- `GET /api/trackers` 返回 `{ trackers: [{ slug, name, status: "active" \| "archived", fields: [{ key, label, type, enumValues?, unit?, status: "active" \| "disabled"? }], createdAt, archivedAt? }] }`；字段 `type` 取 `boolean` / `number` / `enum` / `text` / `time` 五种（决策「记录项化日程域」）；`status: "disabled"` 为已停用字段（历史数据保留、不再记录）。
- `GET /api/records` 返回记录项原生形状：`days` 以 `YYYY-MM-DD` 为键，值为 `{ [tracker_slug]: { [field_key]: 值 } }`；记录项当月无任何记录时不占用键。
- server 的具体状态码、错误文本和响应结构以 `apps/server/src/infrastructure/http/contract.ts` 为准。所有 API（只读与 v1 提案/认证/记忆）的错误响应统一为 `{ "error": { "code", "message" } }`。

### 提案生命周期

- 提案包含 `proposal_id`、过期时间和服务端保存的 operations；客户端不能提交或修改 operations。
- 确认和取消只使用 URL 中的 `proposal_id`。重复确认返回已保存结果，不重复写入；取消或过期后的提案不能再次确认。
- 提案 TTL 10 分钟。
- 提案亮出 30 秒未取消即由服务端自动写入（2026-10-05 用户决策）：与人工确认同一条 commit 路径，幂等且不豁免冲突检测；取消是唯一拒绝方式，窗口 30 秒。
- 提案动作四类：字段写入（现行）、`create_tracker`（名称 + 字段定义）、`archive_tracker`、`amend_tracker`（只加字段/停字段）；创建/归档/调整记录项同样仅凭 `proposal_id` 确认。

### 关键规则

- AI 只收到指令文字、采集时间、时区和严格输出 schema；schema 与提示词字段清单由全部活跃记录项定义动态生成（无活跃项时 operations 为空集）；AI 不接收日程内容、数据库路径、密钥、Shell 或可执行工具。
- AI 输出必须经过 JSON/schema 校验、日期/记录项/字段/枚举校验后才生成提案；未定义字段与枚举外值确定性拒绝并转追问。否定语义只置布尔 `false`：解析是无状态的，早前记录的旧明细不由指令自动清理（显式说「清掉 X」才产出 unset）。
- 记录项定义规则：slug 与名称唯一（创建提案在校验层拒绝冲突，错误消息带冲突项名称）；slug 与字段 key 不可用保留字（如 `calendar`——月历「全部」视图键）；单选枚举至少两个值；同时活跃记录项 ≤12，超出要求先归档。
- 调整（amend）规则：只允许加字段（新 key 不得与任何已有字段冲突）与停用字段（key 必须是当前未停用字段；至少保留一个未停用字段）；禁止改名、改 slug、改字段类型、删数据。停用是定义标记：历史记录值原样保留、读取宽容展示照旧语义，日常记录与 AI 提示词只含未停用字段。
- 读取宽容、写入严格：历史数据遇到未登记枚举值按原文展示不报错；写入一律过当前定义校验。
- 提交时在 SQLite `BEGIN IMMEDIATE` 事务内重新读取目标字段并与提案 expected 状态比较，再经进程内串行队列写入；任一步失败整体回滚。
- 写入是字段级修改：保留无关字段，只修改或删除目标字段。
- 归档记录项：日常写入提示词不含已归档项，相关指令走"无法识别 → 追问"路径；归档不删数据，月历查看方式收起、历史可查（日详情在该日有数据时显示）。
- 用户路径：对话页输入自然语言 → 意图路由进入日程路径 → 信息不足返回歧义追问（不创建提案）→ 消息内提案卡核对差异 → 确认或取消。任何取消、过期、AI 失败或校验失败都不能写入日程。
- 全部记录项同表存储（决策「记录项化日程域」）；迁移走顺序迁移表，失败不落版本，`pnpm run validate` 为迁移后门禁。

### 异常与边界

- 空文本、超长文本、非 JSON、额外请求字段或错误方法在调用 AI 前拒绝。
- 月份自记录派生（决策「记录项化日程域」第三次修订）：目标月份无任何条目时，提案标记需要创建月份；确认后首笔写入即建月，无记录的月份不存在（读取返回 404 MONTH_NOT_FOUND）。
- 当前字段与生成提案时不同则整条提案冲突，不产生任何数据库变更。
- AI 超时、限流或不可用时返回脱敏错误，不泄露上游响应和密钥。
- Memory 不可用时跳过上下文和摘要写入，不阻断日程流程。
- 显式 `false`、数值 `0`、空数组和缺失字段必须分别展示和比较。
- 字段类型误配（次数填了"很多"）：确定性校验拒绝、转澄清追问。

## 安全边界

- 必须：所有写入走"生成提案 → 用户核对 → 使用 URL 中的 `proposal_id` 确认"；确认可为显式点击，也可为发送下一条消息的隐式确认，"取消"是唯一拒绝路径。记录项的创建、归档与调整同样走提案确认。
- 禁止：AI 或 Web 直接读写 `data/schedule.db`；客户端提交 operations、文件路径或超出契约的数据；用户或 AI 绕过记录项定义发明字段。
- 禁止：写入测试触碰正式日程库——提案 API 的写入测试必须使用临时 SQLite 数据目录。

## 验收

- 未确认、取消、过期和歧义追问不修改日程数据；重复确认不二次写入；字段冲突拒绝整条事务；更新时无关字段保留、目标字段被替换或删除；注入的多分类失败回滚为提交前的完整领域状态（自动化测试覆盖，见 `apps/server/test/` 与根 HTTP 集成测试）。
- 空库起步：没有任何预装记录项；创建（含枚举字段）→ 连续多日记录 → 归档全程仅凭自然语言与提案确认，无代码改动；重名创建被拒；归档后写入指令走追问；AI 产出被限制在定义内（未定义字段/枚举外值 422 转追问）。
- v4→v5 升级：旧库（内置四类 + 历史数据）升级后三张表清空、`trackers` 无 builtin 列、幂等重开；升级前停机备份由部署方执行（WAL 注意事项见运维文档 local-and-private-access.md 6.1）；空库通过 `pnpm run validate` 属合法状态。
- 真实 AI 调用依赖本地密钥，不属于普通自动化测试，由 `pnpm run verify:ai` 与用户实测承担；验证记录见 Git 历史。

## 开放问题

- 无（去内置化已定稿实施，见「决策记录」；字段编辑、频率/期限引擎、跨项统计为其记录的远期问题）。

## 决策记录

本域历史决策的背景与取舍。只追加、不改写；实施细节以代码与测试为准，完整原文见 Git 历史。

### 2026-08-31 · 采用 SQLite 作为本地日程数据源

**背景**：JSON 方案已实现字段校验与可读文件，但多分类提交需要自维护事务日志、临时文件与崩溃恢复；且本地与未来服务器要求各自的数据库。
**取舍**：SQLite 原生事务直接保证「全部成功或全部回滚」，单文件一致性备份比多文件原子替换可靠；驱动选 `better-sqlite3`（同步 API，与既有事务语义一致）而弃 Node 内置实验性 `node:sqlite`。被否方案：继续 JSON（要长期维护原子替换与崩溃恢复）、SQLite 内存整块 JSON（字段查询与约束有限）、本地与服务器自动同步（需要设备身份与冲突解决，用户选择两环境完全独立）。公共 HTTP 契约不变，存储变化客户端无感知。
**前置演变**：2026-08-09 YAML 唯一数据源（可读性优先）→ 2026-08-15 改 JSON + JSON Schema（机器校验），两者均已被本决策替代。

### 2026-09-18 · 记录项化日程域（tracker 成为一等公民）

**背景**：能记什么原先写死在全链路（四张分类表 + 硬编码字段、AI schema 与提示词）；新增阶段性跟踪维度（如腕管综合症）要全链路改代码，而内置四类只是"恰好还没停"的四个实例。
**取舍**：统一模型 `trackers`/`tracker_fields`/`tracker_entries`（定义即数据，按日一行 JSON）——与既有「日期→字段映射」的领域形状同构，迁移与读写映射最直接；内置四类的跨字段规则与 Web 特调渲染保留代码、按 slug 挂接（安全子集，强行通用化会放大回归面）；字段类型收敛五种（布尔/数值/单选枚举/文本/时刻），不做多选、计数器与等级；提案动作新增 `create_tracker`/`archive_tracker`/`amend_tracker`——amend 只允许加字段与停用字段（真实盲测暴露"收窄字段"需求后同日收紧），禁止改名、改类型、删数据；月份自条目派生，空月份不存在，首笔写入即建月。
**后续**：内置特调层已由 2026-10-09 决策整体移除。

### 2026-09-27 · 抽取规则文案归 schedule 域

**背景**：AI 适配层文件混装了两类职责——日程抽取规则文案（来源于域内数据结构与校验规则，是日程领域知识）与请求消息组装（AI 传输细节）；新增记录类要改 infrastructure 文件。
**取舍**：域知识归域、传输归基础设施——与手账域 `operations.ts` 同型，是垂直域依赖方向的顺向运用，零新增跨域依赖边；迁移以「拼装产物逐字节不变」验证，承诺原样、只改归属。判断标准成文：属于某域的知识下沉该域（跨域共享业务资产的归属后来由 ADR「AI 层业务部分归域」改判为主要消费域、经装配注入）。

### 2026-10-04 · 迁移表基线合并（v0→v4 直达）

**背景**：四步迁移链里 v1→v2 搬运对现存数据永不执行（本地与线上库均 v4），但整条链是新环境建库与播种内置四类的活代码，不可删。
**取舍**：用户确认所有备份已升级或明确放弃 v1–v3 后执行收敛——迁移表改为单步 v0→v4 直达（事务内建三张 tracker 表并播种内置四类），v1–v3 旧库从「可升级」改为「明确拒绝打开」且拒绝不改动文件；`MigrationStep` 改显式 `from`/`to`，此后升级 schema 仍只追加新项、不改基线。
**后续**：2026-10-09 决策按用户指令改写基线（不再播种、去 builtin 列、基线直达 v5）——「不改基线」的约定就此被用户决策显式取代。

### 2026-10-09 · 去内置化与数据清零（记录项完全用户自定义）

**背景**：内置四类的特调层（静态白名单、schema、提示词、提案卡文案、双端手写视图）使用户无法按自己的生活重组分类；用户在方案对齐中明确：不要预装分类、现有四类与历史数据一并清零（备份在手）。
**取舍**：删除 `builtin` 概念与全部四类特调，校验/schema/提示词/文案/页面单轨按定义生成；新库 v0→v5 直达且不播种，空系统起步（`tracker_actions.create` 为唯一入口）；v4→v5 单事务清空三张表并重建 `trackers` 去 builtin 列，v1–v3 拒绝不变；锻炼/习惯的跨字段特调校验与否定清理随之删除，只留通用类型校验；月历摘要改通用规则（布尔 x/y、时刻、首个枚举/数值、兜底「已记录」）。回退条件：备份未丢弃前可整库回退到 v4，**须连代码一起回退**（新代码会再次清零旧备份；步骤见运维文档 local-and-private-access.md 6.2）。完整取舍见 ADR「日程记录项完全用户自定义」。
