# 访问令牌:多一种凭证,同一套 API

[English](access-tokens.md) | 简体中文

访问令牌(access token)让所有者自己的程序 —— 自建页面、脚本、智能体 —— 用请求头里的令牌代替登录 Cookie,调用自带 Web 应用调用的同一组 `/api` 路由。令牌代表所有者,从来不是另一个用户。

**理由:API 之前只能通过浏览器会话到达,所以每个客户端都得是随包发布的 SPA。在同一组路由上加第二种凭证,API 就开放了,却不用再维护第二套 API。**

## 为什么

- **一套 API。** 没有 `/api/v1`,没有并行接口:令牌打开的就是自带 Web 应用在用的东西,一个功能只做一次。
- **是所有者,不是账号。** 部署只有一个用户;令牌是证明"我是所有者"的另一种方式,带一个名字、一个档位、一个撤销按钮。
- **便宜之处就做最小权限。** 令牌存在页面存储和脚本配置里,比 HttpOnly Cookie 更容易泄露。只读令牌限定了泄露的损失上限。

## 模型

1. **两个档位。** `read` 调用所有 GET;`write` 包含 `read` 和其余所有方法。路由可以用 `config.scope` 另作声明;按方法取默认值,意味着新路由一落地就被覆盖。聊天算 `write` —— 一句话可能落成一笔账。
2. **仅会话的路由。** `config.sessionOnly` 把路由留给浏览器会话:AI 设置(里面有供应商密钥)、令牌管理、修改密码、重置记忆。令牌 —— 包括 `write` —— 返回 `SESSION_REQUIRED`。
3. **只存摘要。** `data/auth.db` 里每个令牌一行 `access_tokens`:SHA-256 摘要、供列表显示的末四位、档位和时间戳。明文只在创建时返回一次。
4. **只走请求头,不进 URL。** `Authorization: Bearer <token>`。查询串会明文进日志,请求头不会。带了令牌就只由令牌决定这次请求 —— 旁边的 Cookie 被忽略。
5. **守卫默认安全。** 每条 `/api` 路由仍然挂着守卫。守卫现在解析出一个主体(会话或令牌),并检查路由的规则,只在一处 —— 组合根安装的那个钩子里。
6. **默认永不过期。** 令牌可以带过期时间;过期的令牌和被撤销的一样返回 401。
7. **MCP 网关也用这同一种凭证。** 网关原计划的静态 `TOBY_MCP_TOKEN`([mcp-gateway.md](mcp-gateway.zh.md))让位给这些令牌:网关落地时,它的调用方用它们鉴权。

## 刻意不进第一版的

- **跨域。** 别的源上的浏览器页面把 `/api` 代理成同源,开发服务器就是这么做的。等出现第一个没法代理的页面再加白名单。
- **按请求归因。** 只记录"最近使用时间":traces 不存任何东西,也没有哪一行记录是哪把令牌写的。
- **更细的档位。** 只有两档,按列表存储,以后可以加。
- **限流。** 沿用登录的姿态 —— 单用户服务,挡在运维者自己的网络边界之后。

## 测试

规则单独测(`access.ts`),令牌存储对着真实的 sqlite 文件测,生产装配经 `app.inject` 测:两个档位、每一条仅会话路由、无效 / 过期 / 已撤销的令牌,以及 Cookie 与令牌同时出现时的优先级。根目录的 HTTP 集成测试在真实进程上创建令牌并用它调用 API。
