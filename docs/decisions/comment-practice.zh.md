# 如何编写代码注释

[English](comment-practice.md) | 简体中文

**写代码说不出来的那句话。** 机器从不读注释——读的是人和 AI;也没有任何东西检查注释:代码错了测试会红,注释错了什么都不会发生。所以每条注释要么配得上它占的那一行,要么就是在原地腐烂。

## 动笔之前

按顺序试:**改名 → 收窄类型 → 重构 → 加测试 → 注释**。注释排最后,因为它是唯一没有任何东西验证的通道。

只问一个问题:_删掉它,读者会不会丢一个从这里的命名和类型拿不回来的事实?_ 会 → 写。不会 → 不写。

## 六种好注释

| 类型   | 说什么                                        | 例子                                   |
| ------ | --------------------------------------------- | -------------------------------------- |
| 为什么 | 原因:约束、取舍、放弃的备选                   | `// 重试一次:提供方 30 秒掐掉空闲连接` |
| 不变量 | 未来修改不许破坏的规矩                        | `// 全部落库,或全不落`                 |
| 契约   | 调用方猜不到的:单位、null、顺序、去重、一次性 | `/** 金额为整数分;0 合法 */`           |
| 警告   | 危险,以及"修好它"的代价                       | `// WARNING:空 body 必须解析成 {}`     |
| 定位   | 一行:这里是什么、邻居在哪                     | `/** SQL 层在 repository.ts */`        |
| 待办   | 带归属的 TODO                                 | `// TODO(#123):v2 上线后删掉`          |

契约只从签名评判。"读一遍实现就知道了"永远删不掉一条契约——调用方不读实现。

## 六种坏注释

| 坏法         | 长这样                | 修法                          |
| ------------ | --------------------- | ----------------------------- |
| 复述代码     | `// i 加一`           | 删;删了疼就改命名             |
| 分隔线       | `// ===== 配置 =====` | 拆文件                        |
| 讲历史       | `// 像旧解析器那样`   | 仍成立的规矩留下,历史子句剪掉 |
| 引出处       | `// 抄自某某项目`     | 改写成约束;规范/RFC 可以留    |
| 注释掉的代码 | `// const x = …`      | 删——这是版本控制的活          |
| 写作过程     | `// 这里改了很久`     | 删                            |

## 四条规则

1. **同一笔提交**——代码证伪了注释,同一笔提交里更新它。注释和代码打架,是缺陷。
2. **一个家**——每个事实住在强制它的边界上;镜像副本一起改;"同上"永不存在。
3. **删除要证据**——说出是哪个签名、哪行代码、哪个测试扛着这个事实,说不出来就留着。
4. **一行胜五段**——注意力是预算。
