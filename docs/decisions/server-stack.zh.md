# 为什么服务端选这套技术栈

[English](server-stack.md) | 简体中文

## 核心思路

选型只有一个标准:**自托管、单用户、单进程的个人项目,一切为简单和可控让路。**

能少一个进程,就少一个进程;能少一层框架,就少一层框架。

## Fastify

HTTP 框架选 Fastify:**小、快,插件模型直观。**

- 日常要用的东西内置了:JSON 解析、schema 校验、错误处理、路由组织,不用自己一块块拼
- 静态文件、cookie 这类能力以插件按需挂载,核心保持干净
- 不选 Express——太裸,错误处理和校验都要自己组装
- 不选 NestJS——个人项目不需要 IoC 容器和装饰器那套仪式感

## SQLite + better-sqlite3

数据库选 SQLite,这是整个技术栈里最划算的一项。

**一个文件就是一个库。**

- 没有数据库服务:没有端口、没有连接配置、没有开机自启、没有版本升级,少一个会坏的东西
- 备份就是复制文件:`data/` 目录整体拷走就是完整备份,校验和、打包、搬家全是文件操作
- 数据跟着项目走:清空 `data/` 就是干净重来,不在系统里残留任何服务

**同步 API,事务就是函数调用。**

better-sqlite3 是同步调用:没有连接池、没有断线重连、没有异步竞态。一个事务,就是用 begin / commit 包住一段普通代码。这对"提案确认后一次事务写入"的模型特别契合:重读目标、检查冲突、执行写入,整段原子,可推理。

**众所周知的短板,在这个项目里不存在。**

SQLite 的短板是单写者、不适合高并发。而 Toby 本来就只有一个写者(server 单进程),写入又全部走提案确认——低频、事务化,天生就是 SQLite 最舒服的场景。读多写少,WAL 模式下读写互不阻塞;单用户的数据量,连它能力的零头都用不到。SQLite 也是测试最充分的软件之一,可靠性不用怀疑。

**为什么不选 MySQL / PostgreSQL。**

它们要多跑一个守护进程:端口、凭据、连接池、备份工具、升级,运维面直接翻倍;数据库密码又多一份要保管的敏感信息。这些代价换来的能力——高并发、多应用共享、海量数据——本项目一项都用不到。

哪天真出现多进程写入或数据量问题再迁移不迟:数据就在文件里,迁移路径是清晰的。

## zod

**一份定义,同时做运行时校验和类型推导。**

- 外来的数据(AI 输出、HTTP 请求体、环境变量)过完校验才可信,TypeScript 类型随之而来,不用定义写两遍
- 校验失败的信息足够定位到字段,不用猜哪里错了
- 在 AI 链路里承担确定性校验那一关:模型输出的 JSON 合不合 schema,由它说了算,不信提示词

## pino

**结构化日志:快,输出 JSON,够用。**

- 每条日志是带字段的对象,排查时按字段过滤,不用正则去啃文本
- 开销低,不拖请求
- 日志是给自己看的:不引入更重的可观测性套件,一个 pino 到头

## 本仓库的约定

- 生产是单进程:server 同时提供 API 与两个前端页面
- 外来数据(AI 输出、HTTP 请求体)先过 zod 校验,再进业务逻辑
