# 提案确认内核：默许式确认门

[English](actions-kernel.md) | 简体中文

一切写意图 AI 动作都经过同一个共享状态机：`infrastructure/actions-kernel/` (`registry.ts`) 中的
**提案确认内核**。ledger 的提案注册表是它的第一个消费方适配器；chat、
schedule 以及后续所有域都复用它,而不是各自长一套。

## 为什么是默许

产品流程是对话式的:用户说一句话,AI 用一张提案卡回应。在这个流程里,
按下"取消"意味着不——而**窗口期内的沉默意味着执行**。要求每次写入都
显式确认,会把对话变回填表;窗口保住了对话流,笔仍在用户手里——因为
期限前的"取消"能叫停一切。

## 语义(承重,改动需谨慎)

- **30 秒默许窗口。** 待确认提案在窗口期过后自动执行。沉默即同意;只有
  显式取消能叫停。清扫器每秒一跳,实际写入落在期限后约一秒内。
- **10 分钟 TTL 兜底。** 执行一直失败的提案最终硬性过期;过期后返回 410。
- **单飞,永久幂等。** 清扫器与手动确认共享同一次执行;成功后存储的
  结果在每次重复 commit 时原样回放——绝不双重写入。
- **失败保持待定。** 执行器失败时提案保持 pending;每次清扫重试直到
  TTL 将其过期。失败会被记录,绝不静默。
- **重启丢失未确认提案。** 注册表在内存中:只有已提交的数据持久化。
  这是有意为之——未确认的提案从未被用户同意过,重启时丢弃才是诚实的
  行为。因此备份只会包含已提交的数据。
- **线格式契约。** `PROPOSAL_*` 错误码(404/409/410)是 web 客户端匹配
  的字符串;改名 `ACTION_*` 是跨客户端变更,推迟到第二个域接入内核时。
- **保留期。** 过期记录在过期一小时后清除;之后 commit 就是单纯的 404。

## 护栏

- 内核不自起定时器:各域在自己的模块里驱动清扫器,并在 commit 时传入
  各自的执行器。
- 执行器绝不在门外运行:一切写意图 AI 工具都经过提案;绕过提案的
  直写端点都是缺陷。
- 禁区能力(数据库、Shell、文件路径)根本不会成为工具。

## 数字

30 秒默许窗口(对话流的延迟预算)、10 分钟 TTL(给故障存储十倍的
宽限)、1 小时保留期(内存上界)、1 秒清扫节拍(写入落在期限后约
一秒内)。四项都是默认值,可按域覆盖。
