# 分级写入:增量即写,破坏过门

[English](write-confirmation-tiers.md) | 简体中文

## 为什么

- 使用体验说的:30 秒默许窗口早已把自动写变成事实默认,对增量写入而言,事前那一步只剩延迟和一次点击,没有否决价值。产品哲学要由使用检验,使用已经给出答案。
- 写入风险并不均一。追加一笔账和改写主人手工维护的笔记是两个风险等级;一道门同时管两类,对安全的那类收了过路费,对危险的那类又没多解释什么。

## 模型

写入分两级。分级按**操作**粒度,记录在各域的 features 文档;默认规则:纯追加的操作**直写**,覆盖、删除、重定义的操作**门控**。

- **直写级**——事务内立即执行。提案卡**出生即 confirmed**(没有 pending 态),带同样的 before/after 快照加一个 `revertUntil` 时间戳;在聊天流里它是这次写入的凭据。不等 30 秒,不点确认。
- **门控级**——不变:pending、30 秒默许自动写、显式确认、取消为唯一拒绝、10 分钟 TTL。

actions kernel 仍是两级的唯一写入路径——single-flight、事务、留档。两级只差顺序:直写是先执行后留档,门控是先留档后执行。绕过 kernel 的写入端点仍是缺陷。

## 撤回窗口

- 在 `now < revertUntil`(默认 10 分钟——与门控 TTL 同数量级)内,用户可撤回一张出生即确认的卡;撤回在一个事务里套用 before 快照。
- 撤回由用户点击;点击即确认——不再设第二道门。
- 若同记录已被后续写入触碰,撤回按既有冲突语义拒绝:新的写入胜出。
- 这刻意**不是**通用 undo:没有历史浏览,没有多步回退。窗口过后,卡就是普通凭据。

## 依然是红线的

1. 每次写入都经 actions kernel,事务 + single-flight。AGENTS.md、README、system overview 里"确认中心"的句子换成"kernel 中心"。
2. 禁止能力保持不存在;AI 永不替用户确认,也永不替用户撤回。
3. 破坏性操作保留事前门(手账改写/删除/合并、记忆 remove、tracker 新建/修改/归档)。
4. 信任边界不变:任何写入之前都有确定性的服务端校验,两级皆然。

## 迄今的分级

| 域            | 直写                          | 门控                       |
| ------------- | ----------------------------- | -------------------------- |
| ledger        | 追加条目(批量,1–10)           | —                          |
| schedule      | 字段写入                      | tracker 新建 / 修改 / 归档 |
| notes         | 月记新增/追加,topic 新建/追加 | 改写 / 删除 / 合并         |
| memory        | upsert                        | remove                     |
| todo、library | 落地时分配,默认规则适用       | —                          |

主动回合(触发器输入到来时):直写级离场也写——构造上低危;门控级提案在用户看到之前绝不自动写入。
