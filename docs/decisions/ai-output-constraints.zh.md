# AI 输出约束:形状交给 Schema,语义交给代码

[English](ai-output-constraints.md) | 简体中文

## 为什么

生成是采样,不是执行:同一个请求产出的是一个分布。所以约束问题不是"让模型听话",
而是"让错误的草稿被廉价地拦下"——拦截层越靠前、越机械,错误草稿的代价越低。本仓库
把格式约束搬过两次家,每一次都把拦截点提前。

## 三层阶梯

- **提示词承载意图,不承载格式。** 提示词仍然存在——序言、规则、每次运行的上下文;
  `<tools>` 一节由工具元数据生成,改名不会留下过时的提及(细节见
  [ai-pi-runtime.zh.md](ai-pi-runtime.zh.md))。退役的是"用提示词约束格式":
  最早的做法是在提示词里描述 JSON 协议,再从回复的正文中把 JSON 抠出来。服从是
  概率性的,失败在服务端解析时才暴露——那时调用已经付过费——唯一的补救是盲目
  重试一次。
- **工具调用加 JSON Schema 约束形状。** 工具调用是模型原生的结构化输出通道;
  经过 schema 校验的参数在边界处被机器核验,先于任何领域代码运行。格式错的草稿
  作为 tool error 弹回,由模型修复自己的输出——纠错是一个由回合上限兜底的循环,
  不是重试。pi-schema 的 coercion 放宽了接受面,但从不决定放行;领域永远不会
  仅凭 coercion 看到数据。
- **确定性的领域校验决定语义。** schema 永远只能查形状;语义——金额是整数分、
  真实的日历日期、条目边界——手写在各领域里(ledger 的 `validation.ts` 是活例)。
  这条信任边界从第一天起就在,从未移动。

每层一句话:提示词什么都不被信任,schema 只被信任形状,手写的门被信任一切。
