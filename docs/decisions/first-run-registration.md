# First-Run Registration: The Password Lives in the Auth Database

English | [简体中文](first-run-registration.zh.md)

The owner sets the login password on a one-time registration page at first
start, and its hash lives in the auth database. There is no password-less
mode and no password environment variable.

**The reason: the old arrangement tied the credential to deployment
configuration — a hash generated by a script, pasted into `.env`, changed by
editing the file and restarting — and a server without it ran with every
route open. A login system owns its credential: set in the product, stored
with the product's data, changed in the product.**

## Why

- **No open-by-default server.** "Unconfigured means no login" turned a
  forgotten variable into a fully open API. An unconfigured server is now
  closed: nothing opens until the owner registers.
- **One place for the credential.** The hash sits in `data/auth.db` beside
  the other domain data — the same backups, the same `data/` boundary, the
  same rule that only the server writes.
- **No secret hand-off.** The password never leaves the browser except over
  the owner's own channel; there is no hash to generate, copy, or send.

## The model

1. **One row.** `data/auth.db` holds an `owner` table with a single row:
   the scrypt hash and the time it was set. Sessions stay in memory — a
   restart ends every session and keeps the password.
2. **Registration is public by necessity and guards itself.**
   `POST /api/auth/register` works only while no password exists and only
   within ten minutes after the server starts. The row's primary key is the
   arbiter: the first insert wins, a concurrent second one answers
   `ALREADY_REGISTERED`.
3. **A window, not a setup code.** On a server left unregistered, whoever
   reaches the page first would set the password. Ten minutes turns
   "forgotten for a day" into "closed"; a restart reopens it. A setup code
   printed to the console was rejected — it would put a credential in the
   logs and add a step to every deployment.
4. **No default password.** A shipped default is a public credential for as
   long as it goes unchanged; a server-generated password was rejected for
   the same reason a setup code was.
5. **A hard cut.** `TOBY_AUTH_PASSWORD_HASH` is no longer read and is not
   imported: an existing deployment registers again after upgrading. The
   owner chose this over a one-time import — one deployment, one minute of
   work, and no legacy path to retire later.

## Deliberately not in v1

- **Password recovery.** Forgetting the password means stopping the server,
  deleting `data/auth.db`, and registering again. No script writes the
  database; only the server does.
- **A window knob.** Ten minutes is a constant. A variable arrives with the
  first deployment that needs a different one.

## Testing

`app.inject` drives the production assembly with an injected clock: the
window's last millisecond, its expiry, a restart reopening it, the one-time
rule, and the body bounds. The root HTTP integration test registers on a
real process before every suite that needs the API.
