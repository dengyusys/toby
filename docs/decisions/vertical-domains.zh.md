# 为什么选择按业务域组织代码

[English](vertical-domains.md) | 简体中文

## 核心思路

本仓库采用按业务域组织代码的方式,而不是传统的技术分层。

原因很简单:**我更希望代码结构反映业务本身,而不是只反映代码的技术职责。**

项目的技术栈相对稳定,后续开发主要围绕日程、记账等业务功能展开。相比按 Controller、Service、Repository 划分目录,把一个业务域的相关代码放在一起,更符合项目的演进方式。

## 与传统技术分层有什么区别?

传统技术分层按代码的技术职责组织目录(`controllers/`、`services/`、`repositories/`、`models/`):统一管理各类技术角色很清晰,但随着业务域增加,同一个业务的代码会分散到多个目录。业务域切片则把**同一业务**的不同技术职责放在一起:

```text
src/
├── domains/
│   ├── schedule/
│   │   ├── controller.ts
│   │   ├── service.ts
│   │   ├── store.ts
│   │   └── types.ts
│   └── ledger/
│       └── …同构…
├── infrastructure/
└── main.ts
```

例如,修改记账功能时,相关路由、业务逻辑和存储代码都集中在 `domains/ledger/` 中,不必在多个技术目录之间寻找和修改文件。

## 为什么选择业务域切片?

**让代码结构贴近业务变化。** 新增业务域时,通过新增模块并在 `main.ts` 中完成装配,减少对已有模块的影响;每个业务域负责自己的规则、逻辑和数据访问,不直接依赖其他业务域——跨域协作由 `main.ts` 通过明确的接口装配,并且这些约束由 `test/boundaries.test.ts` 中的边界测试机器强制,不依赖开发者自觉。

**让业务逻辑更容易理解和测试。** 一个业务域的主要实现集中在同一个目录中,阅读代码时不必先了解整个项目的技术分层。不依赖框架和基础设施的业务规则可以用普通函数实现,直接进行单元测试,不需要启动 HTTP 服务或连接数据库。

## 在本仓库中

具体边界(域间禁止导入、infrastructure 不依赖业务域、`test/boundaries.test.ts` 边界测试机器强制)由[系统架构总览](../system-overview.zh.md)与 `AGENTS.md` 维护——请直接查阅,此处不再复制一份清单。

这套设计的目标不是追求更复杂的架构,而是让代码组织方式与业务的演进方式保持一致。
