# AI-Assisted Development Practice: Continuously Maintaining Correctness

English | [简体中文](ai-coding-practice.zh.md)

> **Scope**: projects maintained by one person or a small team, with AI agents
> deeply involved in coding. This document is the methodology itself; the
> concrete operating rules for your agents live in your project's agent
> instruction file (e.g. AGENTS.md) — this essay explains why those rules
> should be what they are, and covers what machines do not yet enforce.

---

## 0. Problem definition

The problem development solves is not "how to write correct code once", but:

> **Under incomplete information, shifting requirements, and growing systems, keep making change decisions that are verifiable, revertible, and evolvable.**

AI changes the cost structure, not the problem:

|                     | Traditional development  | AI-assisted development                                                       |
| ------------------- | ------------------------ | ----------------------------------------------------------------------------- |
| Cost of generating  | High                     | Near zero                                                                     |
| Cost of verifying   | Medium                   | **The main bottleneck**                                                       |
| Typical error shape | Obvious: syntax, crashes | **Plausible errors**: consistent style, well-commented, compiles, logic wrong |
| Change size         | Bounded by human stamina | Easily out of control; opportunistic refactors, sweeping rewrites             |

So the center of gravity moves from "writing it right" to "**continuously proving it is still right**."

---

## 1. Axioms and corollaries

### Axiom: correctness is a constraint maintained across changes

Correctness cannot be proven once and held forever. Code, dependencies, data,
requirements, and environments all change; the system keeps drifting from
expectations. Maintaining correctness takes feedback loops — one-shot proofs
cannot do it.

### Corollary 1: lower the cost of each maintenance step

Since maintenance is continuous, make errors surface **earlier, cheaper, and
more reversibly**:

- **Earlier**: caught at decision time beats caught at review beats caught in
  production;
- **Cheaper**: low cost to find and fix, ideally automated — typecheck, lint,
  format, and test are this corollary in concrete form;
- **More reversible**: a fast path back to a known-good state — code via
  reverting single-intent commits, data via backups.

### Corollary 2: recurring error classes are blocked by structure, not memory

The first occurrence of an error is incomplete information; the second
occurrence of the same class is a design failure. A confirmed error must be
converted into a structural constraint (see §6).

### Corollary 3: evidence must be independent of generation

(Specific to the AI era.) If the code and its tests are generated by the same
model in the same context, they **share the same misconception**. Passing
tests then prove nothing — only that the two agree with each other.

## 2. The core loop

```text
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌──────────────┐
   │ Decide  │───▶│ Generate│───▶│ Verify  │───▶│ Ship/Observe │
   │ bounds  │    │  (AI)   │    │evidence │    │ trunk push   │
   │ evidence│    │         │    │→ truth  │    │ CI same set  │
   └─────────┘    └─────────┘    └────┬────┘    └──────┬───────┘
        ▲                             │                │
        │    ambiguous req / falsified│                │ incidents
        │◀────────────────────────────┘                ▼
        │                                     ┌──────────────┐
        └─────────────────────────────────────│  Escalate    │
        new constraints gate the next decision│ ADR/test/lint│
                                              └──────────────┘
```

Each stage of the loop has an owner:

| Stage          | Typical form                                                                   |
| -------------- | ------------------------------------------------------------------------------ |
| Decide         | boundaries and red lines in the agent instruction file, interface contracts,   |
|                | architecture decision records (ADRs), the task's scope statement               |
| Generate       | the agent works inside the repo and produces a diff                            |
| Verify         | the four checks, plus boundary tests and end-to-end integration tests          |
| Ship & observe | trunk push (each approved by a human) + CI as the net; structured request logs |
|                | and one error boundary at runtime                                              |
| Escalate       | ADRs, regression tests, lint rules, runtime guards                             |

Three load-bearing feedback edges:

1. **Verify → decide**: when verification reveals ambiguity or a falsified
   assumption, **go back to the decision** — do not let the AI guess its way
   through. One hard rule worth writing down: when code and documents disagree
   on data / security / public interfaces, stop and ask — never pick a side.
2. **Observe → escalate**: production incidents and test findings go through
   the same escalation flow.
3. **Escalate → decide**: new constraints gate later changes; old constraints
   retire per §6.4.

## 3. Decide: draw the bounds before generating

The decision stage's output is the task's **scope statement**, written into
the task description itself. A solo project needs no "change cards", but the
scope statement does the same job: it is both the AI's instruction and the
baseline the diff is checked against at verification time.

### 3.1 Single intent

**One change does one thing.** Refactors and behavior changes are separate
commits; dependency bumps and feature work are separate commits. The
single-subject Conventional Commit is this discipline in minimal form — if a
second intent doesn't fit on the subject line, split the change.

The reason: decision, verification, and revert costs all grow superlinearly
with diff size. Mixed-intent changes:

- leave the reviewer unable to tell deliberate from accidental edits;
- cannot be partially reverted when something breaks;
- cannot be bisected when a test fails.

Rule of thumb: past ~400 changed lines (excluding generated files and
snapshots), or past one module boundary, consider splitting.

### 3.2 Explicit boundaries

Tell the AI three things:

- **What it may change**: files, modules, functions;
- **What it may not change** — keep a default list; unless the task names it,
  the following are untouchable:
  - the production data directory: not one byte by default;
  - interface contracts and ADRs: changing a contract must be the task's
    intent, with every language mirror updated in the same change;
  - closed error-code unions: new codes go in their definition site only, and
    every client is updated with them;
  - the dependency version list (single source of truth) and the lockfile;
  - CI configuration and boundary tests;
- **What to do when unsure**: stop and ask; never assume.

### 3.3 Define acceptance evidence (the oracle)

**Before generation, answer: what observation would let me believe this is
right?**

Sources of truth, weakest to strongest independence:

| Source                                                | Independence | Note                                              |
| ----------------------------------------------------- | ------------ | ------------------------------------------------- |
| The AI's own "done, all good"                         | None         | **Not evidence**                                  |
| Tests the AI wrote in the same context                | Weak         | May share the same misconception                  |
| Tests the AI wrote in an **isolated context**         | Medium       | another session or model, contract only, no impl  |
| Pre-existing domain tests + end-to-end integration    | Strong       | fake dependencies and temp data, never production |
| Type contracts, input schemas, closed error codes     | Strong       | machine-enforced by typecheck and validation      |
| A human walking the real thing; authorized real calls | Very strong  | against the real world; reported separately       |

Requirement: **every change carries at least one "strong" or better piece of
evidence** — or an explicit note on why that is impossible.

### 3.4 Risk tiers

The tier sets the verification intensity, so not everything runs at maximum
ceremony. Tiers align with a "you changed it, you run it" verification matrix:

| Tier   | Typical scope                                                 | Minimum verification                                         | Human role                |
| ------ | ------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------- |
| **R0** | Docs, comments                                                | Link and stale-path checks + whitespace check                | Read it once              |
| **R1** | Features and fixes inside one module                          | The matrix row's commands + lint + format check              | Review the diff           |
| **R2** | Cross-module wiring, public contracts, error codes, schema /  | Full check + contract sync; architecture-level also gets an  | Review design and diff    |
|        | storage formats, dependency upgrades                          | ADR                                                          |                           |
| **R3** | Production data maintenance, real paid external calls, remote | R2 + before/after **SHA-256** checksum comparison + a revert | **Named authorization for |
|        | deployment                                                    | rehearsal                                                    | every step**              |

A solo project has no "second reviewer"; R3's equivalent is: the human does it
personally, or supervises and approves step by step.

### 3.5 Design the revert before writing code

Answer before coding: **when this breaks, how do I get back to the last good
state, and how long does that take?**

- **Code**: single-intent commits on the trunk revert cleanly; check the
  commit hasn't been built upon first;
- **Data**: back up before touching production data, compare checksums
  before and after;
- **External side effects**: real external calls (paid APIs, remote
  deployments) spend real money and do not roll back — authorize first.

> If the revert plan is "we'll figure it out then", the change is at least R2.

## 4. Verify: approach the truth with evidence after generation

### 4.1 The evidence ladder

```text
weak ───────────────────────────────────────────────────────────────▶ strong
AI claim → human reads diff → scoped tests → full check → CI → production
```

**"The AI says it passes" and "the code looks right" are not evidence.** AI-
generated errors tend to look exactly right. The last rung — structured
request logs, the error boundary's report, audit records on data writes — is
production acting as the final verifier.

### 4.2 The independence principle

Guard against "tests and implementation share one misconception" and "the
agent edits tests to make them pass":

- **Critical tests are read-only** to the agent — boundary and integration
  tests count as instruments; editing them to "make tests pass" is editing
  the ruler to fit the object;
- **Review test diffs separately**: any deleted test, weakened assertion, or
  added `skip` needs a stated reason;
- **Test/production isolation**: tests use temp data directories and fake
  dependencies; production data is never touched. Both a safety red line and,
  for free, independent evidence;
- **Contract first**: the acceptance criteria in interface contracts exist
  before the implementation. Behavior changes edit the contract first; tests
  answer to the contract, not to the implementation.

### 4.3 Review the diff against the intent

Check item by item against the scope statement:

- Files touched outside the declared scope?
- "Drive-by" refactors, renames, reformatting?
- New dependencies? Confirm the package name actually exists before it enters
  the version list — watch for AI-invented names being squatted
  (slopsquatting); major-version bumps are their own commits;
- Deleted code that looks "unused"? It might be somebody's edge-case
  handling.

### 4.4 Where AI code typically goes wrong

| Class         | Typical signs                                                                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Boundaries    | Empty collections, null, zero, max values, time zones, Unicode; **valid vs. missing** — is explicit `false`, `0`, or `""` legal data? Decide deliberately |
| Error paths   | Swallowed exceptions, happy-path-only, unbounded retries                                                                                                  |
| Concurrency   | Races, non-atomic check-then-act, shared mutable state                                                                                                    |
| Resources     | Unclosed connections or files, unbounded caches, N+1 queries                                                                                              |
| Security      | Concatenated SQL or shell, hardcoded secrets, over-broad permissions, unvalidated input                                                                   |
| Hallucination | Calls to nonexistent APIs or parameters, outdated library idioms                                                                                          |
| Silent decay  | Errors papered over with defaults; empty catch blocks that make tests "pass"                                                                              |

### 4.5 When you must go back to deciding

Any of these: **stop generating, return to the decision stage**:

- The requirement has two reasonable readings;
- The implementation needs something from the "do not touch" list;
- The same failure has survived 2–3 fix rounds — the problem definition is
  probably wrong;
- The diff is far larger than expected.

> Letting an AI iterate on an ambiguous requirement is the most expensive way
> to work.

## 5. Ship and observe: production is the final verifier

Tests only cover what you **already thought of**. A small self-hosted setup
has no canary, feature flags, or shadow traffic — but the principles hold;
they take a different shape.

### 5.1 Shipping code

- **Up front**: the full check is green locally;
- **Gate**: every commit and push needs explicit human approval — the release
  decision always belongs to a person; agents never auto-commit;
- **Net**: CI runs the same checks after every push, a post-hoc safety net;
- **Rollback**: single-intent commits revert cleanly. Write down beforehand
  what triggers a straight revert — judging "is this blip a problem" after
  the fact is easily captured by sunk costs.

### 5.2 Traceable changes

- Single-subject Conventional Commits: every deployment maps to one intent;
- Structured request logs + one error boundary (errors carry the request id;
  the 500 report keeps only a stack, never sensitive content);
- Audit records on data writes — every write can answer "who, when, what";
- When something breaks, "what changed recently?" is answerable in minutes.

## 6. Escalate: lock lessons into structure after stepping on a rake

### 6.1 The hardness ladder

| Level  | Form                                   | Typical instances                                                                                        |
| ------ | -------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **L0** | Memory, verbal agreement               | — (no constraint deserves to stay here)                                                                  |
| **L1** | Documents                              | agent instruction file, interface contracts, README                                                      |
| **L2** | Reviewer attention                     | in a solo project, review = reading your own diff line by line; fails when tired                         |
| **L3** | Lint, static analysis, CI              | lint rules, format checks, the CI set; compiler switches that make some constructs **unwritable**        |
| **L4** | Tests, regression tests above all      | boundary tests (module isolation, dependency direction), domain tests, end-to-end integration, fake deps |
| **L5** | Types, interface design, architectural | deterministic validation as the single write gate; auth on by default with explicit opt-out; closed      |
|        | isolation, runtime guards              | error codes; dangerous capabilities **don't even exist as definitions**                                  |

**Escalation means pushing a class of error down this table.** A lesson that
only made it into a document is not blocked by anything.

Typical escalation paths:

| Error / risk                | Former weak constraint                   | Upgraded strong constraint                                                                    |
| --------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------- |
| Modules importing each      | A prose rule in an architecture doc (L1) | Boundary tests: a new module is governed the moment it lands (L4)                             |
| other                       |                                          |                                                                                               |
| Unreliable AI output format | JSON protocol described in a prompt (L1) | Tool calls + schema validation + domain-level deterministic checks (L5)                       |
| Dangerous ops bypassing     | A documented red line (L1)               | Runtime guard: unvalidated writes simply fail (L5)                                            |
| the gate                    |                                          |                                                                                               |
| New route missing auth      | Checklist-style reminder (L2)            | The framework mounts a guard on every route by default; public requires an explicit flag (L5) |

### 6.2 The escalation flow

Every confirmed error answers two questions:

1. **Why could it be written at all?** → a decision- or structure-level
   constraint (the L5 direction);
2. **Why wasn't it caught earlier?** → a verification-level constraint (the
   L3–L4 direction).

Then:

- land it at **the hardest feasible level**;
- **add at least one regression test**, annotated with its origin;
- architecture-level constraints → a new ADR: the why, the decision, and its
  relationship to existing ADRs;
- update L1 in the same wave (instruction file / contracts). That level is a
  supplement — **never the only one**.

### 6.3 Registration: ADRs are the registry

Everything constraint registration needs — origin, content, protected
interest, retirement — is carried by the decision-record directory: the
filename is the ID, the Why section is the origin, the Relationship section
is the supersession graph, "superseded by" is the retirement. No separate
registry.

### 6.4 Constraint retirement

Constraints that only accumulate ossify the system: CI slows down, rules
conflict, false positives train people to bypass them, nobody remembers why a
rule exists.

Review is **trigger-based** — when tripped over, when covered by a harder
constraint, when the module it protected is deleted or rewritten. Retirement
takes the form of:

- an ADR marked superseded;
- deleting a lint rule or a boundary-test amnesty line;
- distinguishing "still intercepting" from "risk gone" — the former is not
  retired.

> Retiring a constraint is itself a change, and goes through decide → verify
> → revertible like any other.

## 7. Change granularity and revertible design

### 7.1 Expand–Contract

Every change to interfaces, schemas, or data formats splits into independent
commits:

```text
1. Expand  : add the new field/interface, old ones untouched    ← revertible anytime
2. Migrate : dual-write, move reads over gradually              ← revertible anytime
3. Verify  : observe the new path stabilizing
4. Contract: remove the old field/interface                     ← the only irreversible
                                                                 step; own commit, own approval
```

### 7.2 The irreversible-operations list

These default to **R3**; agents never execute them on their own:

- Touching production data: maintenance is named by the human, with
  before/after SHA-256 comparison;
- Real paid external calls, remote deployment, writing production data — the
  three red lines of automated testing; running any requires explicit
  authorization in the task, and results are reported separately;
- Force push, rewriting trunk history;
- Shipping a breaking change without the expand step.

## 8. Dividing the work between human and AI

| Stage    | The human (maintainer) owns               | The AI is good at                                                |
| -------- | ----------------------------------------- | ---------------------------------------------------------------- |
| Decide   | intent, boundaries, risk tier, **defining | clarifying questions, enumerating edge cases, drafting the scope |
|          | the acceptance evidence**                 | statement                                                        |
| Generate | reviewing direction drift                 | implementation, boilerplate, mechanical migration                |
| Verify   | judging whether evidence suffices;        | running checks with real output, adversarial tests in an         |
|          | approving R2/R3 changes                   | **isolated context**, first-pass diff review                     |
| Ship     | approving every commit / push; rollback   | summarizing check results, diff-vs-scope comparison              |
|          | decisions                                 |                                                                  |
| Escalate | choosing the level, deciding retirement   | drafting lint rules, regression tests, ADR drafts                |

**Principle: the AI may propose anything, but "what counts as right" and
irreversible decisions belong to the human.**

## 9. Anti-patterns

| Anti-pattern                                           | Problem                                    | The practice instead                                                            |
| ------------------------------------------------------ | ------------------------------------------ | ------------------------------------------------------------------------------- |
| "The AI says the tests pass"                           | Not actually run, or the tests were edited | Attach real output from an actual run                                           |
| AI writes both implementation and tests; tests passing | The two share one misconception            | Contract first; tests isolated with fake dependencies and temp data             |
| is the bar                                             |                                            |                                                                                 |
| One commit = feature + refactor + dependency bump      | Unreviewable, unrevertible in part         | Single intent; single-subject Conventional Commits                              |
| Test fails → tell the AI "fix until green"             | The AI may weaken assertions or edit       | First decide: wrong implementation or wrong test; boundary tests are read-only  |
|                                                        | critical tests                             |                                                                                 |
| After a rake, only update the docs                     | L1 constraints decay quietly               | Push to L3–L5 (typical path: an architecture rule goes from ADR prose to a      |
|                                                        |                                            | boundary test)                                                                  |
| Constraints only ever added                            | Ossified system, habitual bypasses         | ADR supersession, lint cleanup, trigger-based review                            |
| Ambiguous requirement → "let the AI draft something"   | Ambiguity gets baked into code             | Return to deciding; when code and docs conflict, stop and ask                   |
| Revert plan is "we'll see"                             | Improvising during the incident            | Checksum comparison for data maintenance; write the revert path before shipping |

## 10. Measurement: is the practice itself working

Small projects skip dashboards; four signals suffice:

| Signal                       | Measures                                             | Desired trend         |
| ---------------------------- | ---------------------------------------------------- | --------------------- |
| **Recurrence of the same     | Is escalation working                                | → 0                   |
| error class**                |                                                      |                       |
| Detection-stage distribution | where errors are caught: decide / verify / CI / prod | shifted left, earlier |
| Average diff size            | granularity discipline                               | stable, single-intent |
| Full-check duration          | the cost of constraints                              | bounded, not creeping |

> Do not measure "how much code the AI generated". Generation is a cost
> line, not an output line.

---

## 11. One-sentence summary

> **Every change small enough to verify, independent enough to be falsified,
> and ready to revert. Every confirmed error pushed to the level that makes
> it harder to happen again; every constraint that no longer earns its keep,
> removed.**

[DECIDE] before generating

  □ Human approved each commit / push?
