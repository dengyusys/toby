# AI 辅助开发实践：持续维护正确性

[English](ai-coding-practice.md) | 简体中文

> **适用范围**：单人或小团队维护、AI agent 深度参与编码的项目。本文只讲方法论本身；给 agent 的具体操作规则，写在项目的 agent 指令文件里（如 AGENTS.md），本文解释那些规则**为什么应该是那样**，并覆盖尚未被机器强制的部分。

---

## 0. 问题定义

开发要解决的问题，不是"怎样一次写出正确的代码"，而是：

> **信息不完备，需求会变，系统会越长越大。在这样的前提下，要持续做出可验证、可回退、可演进的变更决策。**

AI 改变的是成本结构，问题本身没变：

|                | 传统开发               | AI 辅助开发                                                |
| -------------- | ---------------------- | ---------------------------------------------------------- |
| 生成代码的成本 | 高                     | 接近零                                                     |
| 验证代码的成本 | 中                     | **成为主要瓶颈**                                           |
| 典型的错误形态 | 明显错误，如语法、崩溃 | **看起来合理的错误**：风格一致、注释齐全、能编译，但逻辑错 |
| 单次变更的规模 | 受人力限制             | 容易失控，会顺手重构、大面积改写                           |

所以工作重心要从"写对"挪到"**持续证明它还是对的**"。

## 1. 公理与推论

### 公理：正确性是一种随变更持续维护的约束

正确性无法一次证明后永久成立。代码、依赖、数据、需求、运行环境都在变，系统会持续偏离预期。维持正确性要靠反馈回路，一次性的证明做不到。

### 推论一：降低每次维护的成本

既然维护是持续的，策略就是让错误**更早、更便宜、更可逆地暴露**：

- **更早**：在决策阶段暴露，好过在 code review 暴露，更好过在生产环境暴露；
- **更便宜**：发现和修复的成本低，最好是自动化发现——类型检查、lint、格式化、测试这四件套就是这一条的形态；
- **更可逆**：出错后能快速回到已知的正确状态——代码靠单主题提交的 revert，数据靠备份。

### 推论二：同类错误不能靠人记住，要靠结构挡住

一个错误第一次出现，是信息不完备导致的；同类错误第二次出现，就是系统设计的失败。被确认的错误必须转化成结构性约束（见第 6 节）。

### 推论三：证据必须独立于生成过程

（这条是 AI 时代特有的。）如果代码和它的测试由同一个模型在同一段上下文里生成，它们会**共享同一个误解**。这时测试通过证明不了任何东西，只说明它们彼此一致。

## 2. 核心循环

```text
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌──────────────┐
   │  决策   │───▶│  生成   │───▶│  验证   │───▶│ 发布与观测   │
   │划定边界 │    │ (AI)    │    │证据逼近 │    │ 主干直推     │
   │定义证据 │    │         │    │  真相   │    │ CI 同检查    │
   └─────────┘    └─────────┘    └────┬────┘    └──────┬───────┘
        ▲                             │                │
        │       需求歧义/假设被推翻   │                │ 线上问题
        │◀────────────────────────────┘                ▼
        │                                     ┌──────────────┐
        └─────────────────────────────────────│   约束升级   │
               新约束成为下一次决策的门禁      │ ADR/测试/lint │
                                              └──────────────┘
```

循环的每个阶段都有明确归属：

| 阶段       | 典型形态                                                                  |
| ---------- | ------------------------------------------------------------------------- |
| 决策       | agent 指令文件里的边界与红线、接口契约、架构决策记录（ADR）、任务范围声明 |
| 生成       | agent 在仓库内工作，产出 diff                                             |
| 验证       | 四件套检查，加上边界测试与端到端集成测试                                  |
| 发布与观测 | 主干直推（每次需人批准）+ CI 兜底；运行期靠结构化日志与统一错误边界       |
| 约束升级   | ADR、回归测试、lint 规则、运行时守卫                                      |

三条关键的反馈边：

1. **验证 → 决策**：验证中发现需求有歧义、假设不成立，就**回到决策**，不要让 AI 猜着补全。一条值得写死的硬情形：代码与文档冲突且涉及数据 / 安全 / 公共接口时，停下来问人，不要自己选边。
2. **观测 → 约束升级**：线上问题和测试中发现的问题走同一套升级流程。
3. **约束升级 → 决策**：新约束成为后续变更的门禁，旧约束按第 6.4 节退役。

## 3. 决策：生成之前划定边界

决策阶段的产出是一次任务的**范围声明**，直接写在任务描述里。单人项目不需要"变更卡片"这种协调开销，但范围声明要承担同样的职能：既是给 AI 的指令，也是验证阶段对照 diff 的基准。

### 3.1 单一意图

**一次变更只做一件事。** 重构和行为变更分开提交，依赖升级和功能开发分开提交。单行主题的 Conventional Commit 是这个纪律的最小形式——一行写不下第二个意图，说明该拆了。

原因在于决策、验证、回退三者的成本都随 diff 规模超线性增长。混合意图的变更有几个问题：

- 审查者分不清哪些改动是有意的；
- 出问题时无法只回退其中一部分；
- 测试失败时无法定位是哪个意图引入的。

经验阈值：单次变更的 diff 超过约 400 行（不含生成文件、快照），或者涉及超过一个模块的边界，就应该考虑拆分。

### 3.2 明确边界

告诉 AI 三件事：

- **可以改什么**：文件、模块、函数的范围；
- **不许改什么**——准备一份默认清单，除非任务明确点名，以下一律不动：
  - 生产数据目录：默认一个字节不碰；
  - 接口契约与 ADR：改契约本身须是任务意图，且双语或多语言镜像同改；
  - 对外错误码的闭集联合类型：新码只加在定义处，并同步所有客户端；
  - 依赖版本清单（单一事实来源）与 lockfile；
  - CI 配置与边界测试；
- **不确定时怎么办**：停下来提问，不要自行假设。

### 3.3 定义验收证据（Oracle）

**在生成之前回答：什么现象能让我相信它是对的？**

真相来源按独立性从弱到强排列：

| 真相来源                                         | 独立性 | 说明                                       |
| ------------------------------------------------ | ------ | ------------------------------------------ |
| AI 自述"已完成、没问题"                          | 无     | **不算证据**                               |
| AI 在同一上下文中写的测试                        | 弱     | 可能共享同一误解                           |
| AI 在**隔离上下文**中依据规格写的测试            | 中     | 另一次会话或另一个模型，只看契约不看实现   |
| 既有的域测试 + 端到端集成测试                    | 强     | 用假依赖与临时数据，天生独立于生产         |
| 类型契约、输入 schema、闭集错误码                | 强     | 由类型检查与确定性校验机器强制             |
| 人在真实环境实际走一遍；被明确授权的真实外部调用 | 很强   | 直接对照真实世界；结果与本地自动化分开报告 |

要求：**每次变更至少有一项"强"及以上的证据**，或者明确记录为什么无法提供。

### 3.4 风险分级

风险等级决定验证强度，避免所有变更都按最高标准走流程。分级与"改了什么，就跑什么"的验证矩阵对齐：

| 等级   | 典型场景                                                  | 最低验证要求                                | 人工介入               |
| ------ | --------------------------------------------------------- | ------------------------------------------- | ---------------------- |
| **R0** | 文档、注释                                                | 检查链接与旧路径引用 + 空白字符检查         | 自己读一遍             |
| **R1** | 单模块内的功能与修复                                      | 矩阵对应行的命令 + lint + 格式检查          | 审 diff                |
| **R2** | 跨模块接线、公共契约、错误码、schema / 存储格式、依赖升级 | 全量检查 + 契约文档同步；架构级另加 ADR     | 审设计与 diff          |
| **R3** | 生产数据维护、真实付费外部调用、远程部署                  | R2 + 前后 **SHA-256** 校验和比对 + 回退演练 | **每一步都要点名授权** |

单人项目没有"双人审查"，R3 的等价物是：人亲自执行，或逐步监督、逐步批准。

### 3.5 预先设计回退

在写代码之前就要回答：**出问题时怎么回到上一个正确状态？要花多久？**

- **代码回退**：主干上是单主题提交，直接 revert；revert 前确认没被后续提交依赖；
- **数据回退**：动生产数据前先备份、前后比对校验和；
- **外部副作用**：真实外部调用（付费 API、远程部署）花的是真金白银，不可回退，所以必须先授权。

> 如果回退方案是"到时候再想"，那这次变更至少是 R2。

## 4. 验证：生成之后用证据逼近真相

### 4.1 证据层级

```text
弱 ────────────────────────────────────────────────────────────▶ 强
AI 声称 → 人读 diff → 相关测试 → 全量检查 → CI → 生产观测
```

**"AI 说没问题"和"代码看起来对"都不算证据。** AI 生成的错误代码往往恰好"看起来对"。最后一档——结构化请求日志、统一错误边界的报告、数据变更的审计记录——是生产环境作为最终验证的形态。

### 4.2 独立性原则

防止"测试和实现共享同一个误解"，以及"agent 为了让测试通过而修改测试"：

- **关键测试只读**：边界测试与集成测试对 agent 视同只读——改它们来"让测试通过"等于改尺子量自己；
- **测试 diff 单独审**：任何删除测试、放宽断言、加 `skip` 的改动都要说明理由；
- **测试与生产隔离**：测试用临时数据目录与假依赖，生产数据一个字节不碰。这条既是安全红线，也顺带保证了测试证据的独立性；
- **契约先行**：接口契约里的验收标准先于实现存在。行为变更先改契约，测试对契约负责，而不是对实现负责。

### 4.3 审查 diff 是否超出意图

对照范围声明逐项检查：

- 有没有改动声明范围之外的文件？
- 有没有"顺手"的重构、重命名、格式化？
- 有没有新增依赖？进版本清单前确认包名真实存在——警惕 AI 编造的包名被抢注（slopsquatting）；大版本升级单独提交；
- 有没有删除看起来"没用"的代码？那可能是某个边界情况的处理。

### 4.4 AI 代码的高发问题

| 类别     | 典型表现                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------- |
| 边界条件 | 空集合、null、零值、最大值、时区、Unicode；**有效值与缺失值的区分**——显式 `false`、数字 `0`、空串是不是合法数据，要想清楚 |
| 错误路径 | 吞掉异常、只处理 happy path、重试没有上限                                                                                 |
| 并发     | 竞态、非原子的"先检查再执行"、共享可变状态                                                                                |
| 资源     | 连接或文件未关闭、无界缓存、N+1 查询                                                                                      |
| 安全     | 拼接 SQL 或 shell 命令、硬编码密钥、过宽的权限、未校验输入                                                                |
| 幻觉     | 调用不存在的 API 或参数、使用过时的库版本写法                                                                             |
| 静默降级 | 用默认值掩盖错误，用空的 catch 块让测试"通过"                                                                             |

### 4.5 什么时候必须回到决策阶段

出现以下任一情况，**停止生成，回到决策**：

- 发现需求有两种合理解释；
- 实现需要改动"不许改"清单里的东西；
- 同一问题连续修了 2–3 轮仍然失败，说明问题定义可能有误；
- diff 规模远超预期。

> 让 AI 在需求歧义上反复试错，是成本最高的工作方式。

## 5. 发布与观测：生产环境是最终验证

测试只能覆盖你**已经想到**的情况。小团队自托管没有灰度、feature flag、shadow 流量的基础设施，但这一节的原理没有失效——它换了一个形态。

### 5.1 代码的发布

- **前置**：全量检查本地绿灯；
- **门禁**：每次 commit 与 push 都要人明确批准——发布决定权永远在人，agent 不得自动提交；
- **兜底**：CI 在每次 push 后跑同样四项，事后安全网；
- **回滚**：单主题提交直接 revert。发布前写下"什么情况直接 revert"——事后再判断"这个波动算不算问题"，很容易被沉没成本左右。

### 5.2 变更可追溯

- 单行主题的 Conventional Commit：每次部署都能对应到一次意图；
- 结构化请求日志 + 统一错误边界（错误带请求 id，500 报告只带 stack 不带敏感内容）；
- 数据变更留审计记录——每次写入都能回答"谁、何时、写了什么"；
- 出问题时，几分钟能回答"最近改了什么"。

## 6. 约束升级：踩坑之后把教训锁进结构

### 6.1 约束的硬度阶梯

| 层级   | 形式                                 | 典型实例                                                                                               |
| ------ | ------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| **L0** | 记忆、口头约定                       | ——（没有任何约束该停在这一层）                                                                         |
| **L1** | 文档                                 | agent 指令文件、接口契约、README                                                                       |
| **L2** | 审查时的注意力                       | 单人项目的审查 = 自己逐行读 diff，疲劳时失效                                                           |
| **L3** | lint、静态分析、CI                   | lint 规则、格式检查、CI 四项；编译器开关让某些写法**写不出来**                                         |
| **L4** | 测试，尤其回归测试                   | 边界测试（模块隔离、依赖方向）、域测试、端到端集成、假依赖测试                                         |
| **L5** | 类型、接口设计、架构隔离、运行时守卫 | 确定性校验作为唯一写入门禁；鉴权默认开启、公开路由显式 opt-out；闭集错误码；危险能力**连定义都不存在** |

**约束升级的含义，是把同一类错误往表格下方推。** 只写进文档的教训，没有被结构挡住。

几个典型的升级路径：

| 错误 / 风险         | 曾经的弱约束                 | 升级后的强约束                                        |
| ------------------- | ---------------------------- | ----------------------------------------------------- |
| 模块之间直接 import | 架构文档里的文字规则（L1）   | 边界测试：新模块从文件系统被发现即受管辖（L4）        |
| AI 输出格式不可靠   | 提示词里描述 JSON 协议（L1） | 工具调用 + schema 校验 + 业务层确定性验证的阶梯（L5） |
| 危险操作绕过门禁    | 文档红线（L1）               | 运行时守卫：没过校验的写入直接失败（L5）              |
| 新路由忘挂鉴权      | checklist 式提醒（L2）       | 框架层默认给所有路由挂守卫，公开须显式声明（L5）      |

### 6.2 升级流程

每个被确认的错误都要回答两个问题：

1. **为什么能写出来？** → 对应决策或结构层面的约束（L5 方向）；
2. **为什么没被更早发现？** → 对应验证层面的约束（L3–L4 方向）。

然后：

- 选择**可行的最硬一层**落地；
- **至少加一个回归测试**，在测试中注明来源；
- 架构级约束 → 新 ADR：动机（Why）、决策本体、与既有 ADR 的关系；
- 同步更新 L1（指令文件 / 契约文档）。这一层是补充，**不能只做这一层**。

### 6.3 登记：ADR 就是登记表

约束登记的全部需求——来源、内容、保护对象、退役——由决策记录目录承担：文件名即 ID，Why 节即来源，Relationship 节即关联与覆盖关系，supersede 即退役。不另设登记表。

### 6.4 约束退役

只增不减的约束会让系统僵化：CI 越来越慢，规则互相冲突，误报让人习惯性绕过，没人记得某条规则为什么存在。

复审是**触发式**的——被它绊倒时、被更硬的约束覆盖时、它保护的模块被删除或重写时。退役的形态：

- ADR 标记 supersede；
- 删 lint 规则、删边界测试的特赦行；
- 零触发要区分"一直在有效拦截"与"风险已消失"——前者不该退役。

> 删除约束也是一次变更，同样要走"决策 → 验证 → 可回退"。

## 7. 变更粒度与可回退设计

### 7.1 Expand–Contract（先扩展、后收缩）

所有涉及接口、schema、数据格式的变更拆成多次独立提交：

```text
1. Expand  ：新增新字段/新接口，旧的保持不变         ← 可随时回退
2. Migrate ：双写，逐步把读取切到新的                 ← 可随时回退
3. Verify  ：观测确认新路径稳定
4. Contract：删除旧字段/新接口                        ← 唯一不可逆的一步，单独提交、单独批准
```

### 7.2 不可逆操作清单

以下操作默认 **R3**，AI 不得自主执行，必须人工批准：

- 触碰生产数据：维护须点名授权，前后 SHA-256 比对；
- 真实付费外部调用、远程部署、写生产数据——自动化测试的三条红线，跑了就要在任务里明确授权，结果单独报告；
- force push、改写主干历史；
- 跳过 expand 直接发布破坏性变更。

## 8. 人与 AI 的分工

| 环节     | 人（维护者）负责                         | AI 适合做                                                     |
| -------- | ---------------------------------------- | ------------------------------------------------------------- |
| 决策     | 意图、边界、风险分级、**验收证据的定义** | 澄清问题、列举边界情况、起草范围声明                          |
| 生成     | 审查方向是否偏离                         | 写实现、写样板代码、迁移机械性代码                            |
| 验证     | 判断证据是否充分，批准 R2/R3 变更        | 跑检查并附真实输出、在**隔离上下文**中写对抗性测试、初审 diff |
| 发布     | 每次批准 commit / push；执行回滚决策     | 汇总检查结果、对比变更摘要与范围声明                          |
| 约束升级 | 判断该升级到哪一层、是否退役             | 起草 lint 规则、回归测试、ADR 草稿                            |

**原则：AI 可以提出任何建议，但"什么算对"和"不可逆的决定"由人负责。**

---

## 9. 反模式

| 反模式                                     | 问题                              | 正确做法                                                  |
| ------------------------------------------ | --------------------------------- | --------------------------------------------------------- |
| "AI 说测试通过了"                          | 没有实际运行，或者测试被改过      | 必须附真实运行的测试输出                                  |
| 让 AI 同时写实现和测试，然后以测试通过为准 | 两者共享同一个误解                | 契约先行；测试与假依赖、临时数据隔离                      |
| 一个提交包含功能 + 重构 + 依赖升级         | 无法审查，无法局部回退            | 单一意图；单行主题的 Conventional Commit                  |
| 测试失败就让 AI "修到通过"                 | AI 可能会削弱断言，甚至改关键测试 | 先判断是实现错了还是测试错了；边界测试视同只读            |
| 踩坑后只更新文档                           | L1 约束容易失效                   | 推到 L3–L5（典型路径：架构规则从 ADR 文字升级成边界测试） |
| 约束只增不减                               | 系统僵化，规则被习惯性绕过        | ADR supersede、lint 清理，触发式复审                      |
| 需求不清时让 AI "先做个版本看看"           | 歧义被固化进代码                  | 回到决策阶段澄清；代码与文档冲突时停下来问                |
| 回退方案"到时候再说"                       | 出事时临场应对                    | 数据维护的校验和比对；发布前写下 revert 路径              |

---

## 10. 度量：衡量这套实践本身是否有效

小项目不做仪表盘，看四个信号就够了：

| 信号               | 衡量什么                                    | 期望趋势         |
| ------------------ | ------------------------------------------- | ---------------- |
| **同类错误复发率** | 约束升级是否有效                            | → 0              |
| 发现阶段分布       | 错误在哪一层被抓住：决策 / 验证 / CI / 生产 | 左移，即更早发现 |
| 平均 diff 规模     | 粒度纪律                                    | 稳定在单主题以内 |
| 全量检查时长       | 约束的成本                                  | 可控，不持续膨胀 |

> 不要看"AI 生成了多少代码"。生成量是成本项，不是产出项。

---

## 11. 一句话总结

> **每次变更都要小到能验证、独立到能被证伪、准备好能回退。每个被确认的错误，都要推到让它更难再次出现的那一层；每条不再有用的约束，都要被移走。**
