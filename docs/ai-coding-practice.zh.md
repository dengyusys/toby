# AI 辅助开发实践：持续维护正确性

[English](ai-coding-practice.md) | 简体中文

> **适用范围**：本仓库——单人维护、AI agent 参与编码的自托管项目。
> **文档定位**：这套方法在 Toby 的落地版。每条原则都指向仓库里已经存在的结构；团队规模的流程（双人审查、灰度放量、约束登记例会）不在此列。给 agent 的操作规则在 [AGENTS.zh.md](../AGENTS.zh.md)，本文解释这些规则**为什么是这样**，并覆盖尚未被机器强制的部分。

---

## 0. 问题定义

开发要解决的问题，不是"怎样一次写出正确的代码"，而是：

> **信息不完备，需求会变，系统会越长越大。在这样的前提下，要持续做出可验证、可回退、可演进的变更决策。**

AI 改变的是成本结构，问题本身没变：

|                | 传统开发               | AI 辅助开发                                                |
| -------------- | ---------------------- | ---------------------------------------------------------- |
| 生成代码的成本 | 高                     | 接近零                                                     |
| 验证代码的成本 | 中                     | **成为主要瓶颈**                                           |
| 典型的错误形态 | 明显错误，如语法、崩溃 | **看起来合理的错误**：风格一致、注释齐全、能编译，但逻辑错 |
| 单次变更的规模 | 受人力限制             | 容易失控，会顺手重构、大面积改写                           |

所以工作重心要从"写对"挪到"**持续证明它还是对的**"。

这句话在本仓库有一个不寻常的注脚：Toby 这个产品本身就在解同一道题——它自己的 AI 每天对用户数据做受限写入。产品给出的答案（actions kernel、写分层、工具 kind 门控）与本文给开发流程的答案，出自同一组公理。本文会反复指出这个对应。

## 1. 公理与推论

### 公理：正确性是一种随变更持续维护的约束

正确性无法一次证明后永久成立。代码、依赖、数据、需求、运行环境都在变，系统会持续偏离预期。维持正确性要靠反馈回路，一次性的证明做不到。

### 推论一：降低每次维护的成本

既然维护是持续的，策略就是让错误**更早、更便宜、更可逆地暴露**：

- **更早**：在决策阶段暴露，好过在 code review 暴露，更好过在生产环境暴露；
- **更便宜**：发现和修复的成本低，最好是自动化发现——本仓库的四件套（typecheck / lint / format / test）就是这一条的形态；
- **更可逆**：出错后能快速回到已知的正确状态——代码靠单主题提交的 revert，产品数据靠 immediate 层的回退窗口。

### 推论二：同类错误不能靠人记住，要靠结构挡住

一个错误第一次出现，是信息不完备导致的；同类错误第二次出现，就是系统设计的失败。被确认的错误必须转化成结构性约束（见第 6 节）。

### 推论三：证据必须独立于生成过程

（这条是 AI 时代特有的。）如果代码和它的测试由同一个模型在同一段上下文里生成，它们会**共享同一个误解**。这时测试通过证明不了任何东西，只说明它们彼此一致。

## 2. 核心循环

```text
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌──────────────┐
   │  决策   │───▶│  生成   │───▶│  验证   │───▶│ 发布与观测   │
   │划定边界 │    │ (AI)    │    │证据逼近 │    │ main 直推    │
   │定义证据 │    │         │    │  真相   │    │ CI 同四项    │
   └─────────┘    └─────────┘    └────┬────┘    └──────┬───────┘
        ▲                             │                │
        │       需求歧义/假设被推翻   │                │ 线上问题
        │◀────────────────────────────┘                ▼
        │                                     ┌──────────────┐
        └─────────────────────────────────────│   约束升级   │
               新约束成为下一次决策的门禁      │ ADR/测试/lint │
                                              └──────────────┘
```

循环的每个阶段在本仓库都有明确归属：

| 阶段       | 本仓库的形态                                                                                                 |
| ---------- | ------------------------------------------------------------------------------------------------------------ |
| 决策       | [AGENTS.zh.md](../AGENTS.zh.md) 的边界与红线、`docs/features/` 契约、`docs/decisions/` ADR、任务里写下的范围 |
| 生成       | agent 在仓库内工作，产出 diff                                                                                |
| 验证       | `pnpm run check` 四件套，含 `test/boundaries.test.ts` 与根 HTTP 集成测试                                     |
| 发布与观测 | main 直推（每次需用户批准）+ CI 同四项兜底；运行期靠 pino 请求日志与错误边界                                 |
| 约束升级   | ADR、边界测试、lint 规则、kernel 红线                                                                        |

三条关键的反馈边：

1. **验证 → 决策**：验证中发现需求有歧义、假设不成立，就**回到决策**，不要让 AI 猜着补全。AGENTS.zh.md 已把一条硬情形写死：代码与文档冲突且涉及数据 / 安全 / 公共接口时，停下来问用户，不要自己选边。
2. **观测 → 约束升级**：线上问题和测试中发现的问题走同一套升级流程。
3. **约束升级 → 决策**：新约束成为后续变更的门禁，旧约束按第 6.4 节退役。

## 3. 决策：生成之前划定边界

决策阶段的产出是一次任务的**范围声明**，直接写在任务描述里。单人仓库不需要"变更卡片"这种协调开销，但范围声明要承担同样的职能：既是给 AI 的指令，也是验证阶段对照 diff 的基准。

### 3.1 单一意图

**一次变更只做一件事。** 重构和行为变更分开提交，依赖升级和功能开发分开提交。本仓库的提交规范就是这个纪律的最小形式：单行主题的 Conventional Commit——一行写不下第二个意图，说明该拆了。

原因在于决策、验证、回退三者的成本都随 diff 规模超线性增长。混合意图的变更有几个问题：

- 审查者分不清哪些改动是有意的；
- 出问题时无法只回退其中一部分；
- 测试失败时无法定位是哪个意图引入的。

经验阈值：单次变更的 diff 超过约 400 行（不含生成文件、快照），或者涉及超过一个模块的边界，就应该考虑拆分。

### 3.2 明确边界

告诉 AI 三件事：

- **可以改什么**：文件、模块、函数的范围；
- **不许改什么**——本仓库有一份默认清单，除非任务明确点名，以下一律不动：
  - `data/`：生产数据，默认一个字节不碰；
  - `docs/features/` 契约与 `docs/decisions/` ADR：改契约本身须是任务意图，且双语镜像同改；
  - `apps/server/src/domains/<domain>/errors.ts` 的闭集联合类型：新错误码只加在域内，并同步两个 web 客户端；
  - `PLAN.md` 的版本矩阵（pnpm catalog 的唯一事实来源）与 lockfile；
  - CI 配置与 `test/boundaries.test.ts`；
- **不确定时怎么办**：停下来提问，不要自行假设。

### 3.3 定义验收证据（Oracle）

**在生成之前回答：什么现象能让我相信它是对的？**

真相来源按独立性从弱到强排列，每一档都给出本仓库的形态：

| 真相来源                                          | 独立性 | 本仓库的形态                                                 |
| ------------------------------------------------- | ------ | ------------------------------------------------------------ |
| AI 自述"已完成、没问题"                           | 无     | **不算证据**                                                 |
| AI 在同一上下文中写的测试                         | 弱     | 可能共享同一误解                                             |
| AI 在**隔离上下文**中依据规格写的测试             | 中     | 另一次会话或另一个模型，只看 `docs/features/` 契约，不看实现 |
| 既有的域测试 + 根 HTTP 集成测试                   | 强     | 用 fake AI 与临时数据目录，天生独立于生产                    |
| 类型契约、zod schema、闭集错误码                  | 强     | `pnpm run typecheck` 与内核校验机器强制                      |
| 人在 dev 环境实际走一遍；被明确授权的真实 AI 调用 | 很强   | 直接对照真实世界；结果与本地自动化分开报告                   |

要求：**每次变更至少有一项"强"及以上的证据**，或者明确记录为什么无法提供。

### 3.4 风险分级

风险等级决定验证强度，避免所有变更都按最高标准走流程。本仓库的分级与 AGENTS.zh.md 的"改了什么，就跑什么"矩阵对齐：

| 等级   | 本仓库典型场景                                                                       | 最低验证要求                                             | 人工介入                   |
| ------ | ------------------------------------------------------------------------------------ | -------------------------------------------------------- | -------------------------- |
| **R0** | 文档、注释                                                                           | 检查链接与旧路径引用 + `git diff --check`                | 自己读一遍                 |
| **R1** | 单域内的功能与修复                                                                   | 矩阵对应行的命令 + `pnpm run lint` + `format:check`      | 审 diff                    |
| **R2** | composition root 接线、`packages/contract`、wire 错误码、schema / 存储格式、依赖升级 | `pnpm run check` 全量 + 契约文档双语同步；架构级另加 ADR | 审设计与 diff              |
| **R3** | `data/` 维护、真实 AI 调用、远程部署                                                 | R2 + 前后 **SHA-256** 校验和比对 + 回退演练              | **每一步都要用户点名授权** |

单人仓库没有"双人审查"，R3 的等价物是：用户亲自执行，或逐步监督、逐步批准。

### 3.5 预先设计回退

在写代码之前就要回答：**出问题时怎么回到上一个正确状态？要花多久？**

- **代码回退**：main 上是单主题提交，直接 revert；revert 前确认没被后续提交依赖；
- **数据回退**：`data/` 维护前备份、前后比对校验和；产品的用户数据不需要你操心回退——immediate 层带回退窗口（默认 10 分钟），gated 层确认前零写入；
- **外部副作用**：本仓库几乎没有（自托管、loopback、Docker 只绑 `127.0.0.1:8629`）；真实 AI 调用花的是真金白银，不可回退，所以必须先授权。

> 如果回退方案是"到时候再想"，那这次变更至少是 R2。

## 4. 验证：生成之后用证据逼近真相

### 4.1 证据层级

```text
弱 ────────────────────────────────────────────────────────────▶ 强
AI 声称 → 人读 diff → pnpm run test → pnpm run check → CI 同四项 → 生产观测
```

**"AI 说没问题"和"代码看起来对"都不算证据。** AI 生成的错误代码往往恰好"看起来对"。最后一档——pino 请求生命周期日志、错误边界 stack-only 的 500 报告、写操作的回执卡片——是生产环境作为最终验证的形态。

### 4.2 独立性原则

防止"测试和实现共享同一个误解"，以及"agent 为了让测试通过而修改测试"：

- **关键测试只读**：`test/boundaries.test.ts` 与根集成测试对 agent 视同只读——改它们来"让测试通过"等于改尺子量自己；
- **测试 diff 单独审**：任何删除测试、放宽断言、加 `skip` 的改动都要说明理由；
- **测试与生产隔离**：本仓库测试用临时数据目录与 fake AI，生产数据一个字节不碰。这条既是安全红线，也顺带保证了测试证据的独立性；
- **契约先行**：`docs/features/` 的验收标准先于实现存在。行为变更先改契约（及其镜像），测试对契约负责，而不是对实现负责。

### 4.3 审查 diff 是否超出意图

对照范围声明逐项检查：

- 有没有改动声明范围之外的文件？
- 有没有"顺手"的重构、重命名、格式化？
- 有没有新增依赖？新增依赖进 pnpm catalog（版本以 `PLAN.md` 矩阵为准），确认包名真实存在——警惕 AI 编造的包名被抢注（slopsquatting）；大版本升级单独提交；
- 有没有删除看起来"没用"的代码？那可能是某个边界情况的处理。

### 4.4 AI 代码的高发问题

| 类别     | 典型表现                                                                                                        |
| -------- | --------------------------------------------------------------------------------------------------------------- |
| 边界条件 | 空集合、null、零值、最大值、时区、Unicode；**本仓库特有**：显式 `false` 与数字 `0` 是有效数据，绝不当"缺失"处理 |
| 错误路径 | 吞掉异常、只处理 happy path、重试没有上限                                                                       |
| 并发     | 竞态、非原子的"先检查再执行"、共享可变状态                                                                      |
| 资源     | 连接或文件未关闭、无界缓存、N+1 查询                                                                            |
| 安全     | 拼接 SQL 或 shell 命令、硬编码密钥、过宽的权限、未校验输入                                                      |
| 幻觉     | 调用不存在的 API 或参数、使用过时的库版本写法                                                                   |
| 静默降级 | 用默认值掩盖错误，用空的 catch 块让测试"通过"                                                                   |

### 4.5 什么时候必须回到决策阶段

出现以下任一情况，**停止生成，回到决策**：

- 发现需求有两种合理解释；
- 实现需要改动"不许改"清单里的东西；
- 同一问题连续修了 2–3 轮仍然失败，说明问题定义可能有误；
- diff 规模远超预期。

> 让 AI 在需求歧义上反复试错，是成本最高的工作方式。

## 5. 发布与观测：生产环境是最终验证

测试只能覆盖你**已经想到**的情况。单人自托管没有灰度、feature flag、shadow 流量的基础设施，但这一节的原理没有失效——它在本仓库换了一个形态。

### 5.1 代码的发布

- **前置**：`pnpm run check` 本地绿灯，这是 AGENTS.zh.md 的硬要求；
- **门禁**：每次 commit 与 push 都要用户明确批准——发布决定权永远在人，agent 不得自动提交；
- **兜底**：CI 在每次 push 后跑同样四项，事后安全网；
- **回滚**：单主题提交直接 revert。发布前写下"什么情况直接 revert"——事后再判断"这个波动算不算问题"，很容易被沉没成本左右。

### 5.2 产品的写入就是渐进发布

Toby 把这一节做成了运行时（[decisions/write-confirmation-tiers.zh.md](decisions/write-confirmation-tiers.zh.md)、[decisions/actions-kernel.zh.md](decisions/actions-kernel.zh.md)）：

- **immediate 层** = 立即执行 + 回退窗口：增量变更一次落库，数分钟内可逆——灰度与回滚的用户级等价物；
- **gated 层** = proposal → 确认：破坏性变更等待人工批准，确认前零写入，取消即零副作用；
- **actions kernel** = 单一写路径、单飞、事务——发布的原子性与可审计性。

### 5.3 变更可追溯

- 单行主题的 Conventional Commit：每次部署都能对应到一次意图；
- pino 请求生命周期日志 + 错误边界只带 stack 的 500 报告（[decisions/server-logging.zh.md](decisions/server-logging.zh.md)）；
- 回执卡片自带 before/after 快照——产品数据的每次写入都有审计记录；
- 出问题时，几分钟能回答"最近改了什么"。

## 6. 约束升级：踩坑之后把教训锁进结构

### 6.1 约束的硬度阶梯（本仓库实例）

| 层级   | 形式                                 | 本仓库实例                                                                                                                                                         |
| ------ | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **L0** | 记忆、口头约定                       | ——（没有任何约束该停在这一层）                                                                                                                                     |
| **L1** | 文档                                 | [AGENTS.zh.md](../AGENTS.zh.md)、`docs/features/` 契约、README                                                                                                     |
| **L2** | 审查时的注意力                       | 单人仓库的审查 = 自己逐行读 diff，疲劳时失效                                                                                                                       |
| **L3** | lint、静态分析、CI                   | ESLint、Prettier、CI 四项；`tsc` 的 `erasableSyntaxOnly` 让 enum / namespace / 构造器参数属性**写不出来**                                                          |
| **L4** | 测试，尤其回归测试                   | `test/boundaries.test.ts`（域隔离、依赖方向、`types.ts` 纯净度）、域测试、根 HTTP 集成、fake-AI 测试                                                               |
| **L5** | 类型、接口设计、架构隔离、运行时守卫 | actions kernel 单一写路径（绕过即缺陷）；session guard 默认开启、公开路由显式 opt-out；`errors.ts` 闭集联合类型；AI 工具 kind 门控，禁用能力**连工具定义都不存在** |

**约束升级的含义，是把同一类错误往表格下方推。** 只写进文档的教训，没有被结构挡住。

本仓库真实发生过的升级：

| 错误 / 风险       | 曾经的弱约束                           | 现在的强约束                                                                                                                                |
| ----------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 域之间直接 import | vertical-domains.md 里的文字规则（L1） | `test/boundaries.test.ts`：新域从文件系统被发现即受管辖（L4）                                                                               |
| AI 输出格式不可靠 | 提示词里描述 JSON 协议（L1）           | 工具调用 + schema 边界校验 + 域内确定性验证的三级阶梯（L5，[decisions/ai-output-constraints.zh.md](decisions/ai-output-constraints.zh.md)） |
| 写端点绕过确认    | 文档红线（L1）                         | 一切写走 kernel，事务、单飞，绕过即缺陷（L5）                                                                                               |
| 新路由忘挂鉴权    | checklist 式提醒（L2）                 | composition root 默认给所有 `/api` 路由挂 session guard，公开须显式 `config: { public: true }`（L5）                                        |

### 6.2 升级流程

每个被确认的错误都要回答两个问题：

1. **为什么能写出来？** → 对应决策或结构层面的约束（L5 方向）；
2. **为什么没被更早发现？** → 对应验证层面的约束（L3–L4 方向）。

然后：

- 选择**可行的最硬一层**落地；
- **至少加一个回归测试**，在测试中注明来源；
- 架构级约束 → 新 ADR：动机（Why）、决策本体、与既有 ADR 的关系；
- 同步更新 L1（AGENTS.zh.md / 契约文档）。这一层是补充，**不能只做这一层**。

### 6.3 登记：ADR 就是登记表

约束登记的全部需求——来源、内容、保护对象、退役——由 `docs/decisions/` 承担：文件名即 ID，Why 节即来源，Relationship 节即关联与覆盖关系，supersede 即退役。不另设登记表。

### 6.4 约束退役

只增不减的约束会让系统僵化：CI 越来越慢，规则互相冲突，误报让人习惯性绕过，没人记得某条规则为什么存在。

单人仓库不做周期性例会，复审是**触发式**的——被它绊倒时、被更硬的约束覆盖时、它保护的模块被删除或重写时。退役的形态：

- ADR 标记 supersede（先例：ai-output-constraints 取代了退役的 ai-integration 的提示词协议）；
- 删 lint 规则、删边界测试的特赦行；
- 零触发要区分"一直在有效拦截"与"风险已消失"——前者不该退役。

> 删除约束也是一次变更，同样要走"决策 → 验证 → 可回退"。

---

## 7. 变更粒度与可回退设计

### 7.1 Expand–Contract（先扩展、后收缩）

所有涉及接口、schema、数据格式的变更拆成多次独立提交：

```text
1. Expand  ：新增新字段/新接口，旧的保持不变         ← 可随时回退
2. Migrate ：双写，逐步把读取切到新的                 ← 可随时回退
3. Verify  ：观测确认新路径稳定
4. Contract：删除旧字段/新接口                        ← 唯一不可逆的一步，单独提交、单独批准
```

产品的写分层就是这个模式在数据层的运行时形态：additive 走 immediate（可回退的 expand），destructive 走 gated（单独批准的 contract）。代码这边照做：先加能与旧路径共存的新路径，稳定后单独提交删除。

### 7.2 不可逆操作清单

以下操作默认 **R3**，AI 不得自主执行，必须人工批准：

- 触碰 `data/`：维护须用户点名，前后 SHA-256 比对；
- 真实 AI 调用、远程部署、写生产数据——自动化测试的三条红线，跑了就要在任务里明确授权，结果单独报告；
- force push、改写 main 历史；
- 跳过 expand 直接发布破坏性变更。

### 7.3 Agent 的执行环境：产品与开发用同一套答案

本仓库给产品里的 AI 定下的约束，与给开发侧编码 agent 的约束互为镜像：

| 给谁的约束 | 产品侧：Toby 的 AI 助手                                  | 开发侧：本仓库的编码 agent                  |
| ---------- | -------------------------------------------------------- | ------------------------------------------- |
| 能力边界   | 工具带 safety kind（read-only / write-intent），策略门控 | 权限模式把关工具调用；AGENTS.zh.md 禁止事项 |
| 禁用能力   | 数据库、shell、文件路径**不作为工具定义存在**            | 不自动 commit / push；不碰 `data/`          |
| 写入形态   | write-intent 工具只产生写草案，效果仍走 kernel           | 代码修改只产生 diff，由人审查               |
| 最终决定权 | AI 永不确认、永不代用户 revert                           | commit 与 push 每次都要用户批准             |

## 8. 人与 AI 的分工

| 环节     | 人（维护者）负责                         | AI 适合做                                                     |
| -------- | ---------------------------------------- | ------------------------------------------------------------- |
| 决策     | 意图、边界、风险分级、**验收证据的定义** | 澄清问题、列举边界情况、起草范围声明                          |
| 生成     | 审查方向是否偏离                         | 写实现、写样板代码、迁移机械性代码                            |
| 验证     | 判断证据是否充分，批准 R2/R3 变更        | 跑检查并附真实输出、在**隔离上下文**中写对抗性测试、初审 diff |
| 发布     | 每次批准 commit / push；执行回滚决策     | 汇总检查结果、对比变更摘要与范围声明                          |
| 约束升级 | 判断该升级到哪一层、是否退役             | 起草 lint 规则、回归测试、ADR 草稿                            |

**原则：AI 可以提出任何建议，但"什么算对"和"不可逆的决定"由人负责。** 这条原则在产品里的镜像，就是 write-confirmation-tiers 的红线：AI 永不确认、永不代用户 revert。

## 9. 反模式

| 反模式                                     | 问题                              | 本仓库的正确做法                                                 |
| ------------------------------------------ | --------------------------------- | ---------------------------------------------------------------- |
| "AI 说测试通过了"                          | 没有实际运行，或者测试被改过      | 必须附 `pnpm run test` 的真实输出                                |
| 让 AI 同时写实现和测试，然后以测试通过为准 | 两者共享同一个误解                | 契约先行（features 文档），测试用 fake AI 与临时目录隔离         |
| 一个提交包含功能 + 重构 + 依赖升级         | 无法审查，无法局部回退            | 单一意图；单行主题的 Conventional Commit                         |
| 测试失败就让 AI "修到通过"                 | AI 可能会削弱断言，甚至改边界测试 | 先判断是实现错了还是测试错了；`test/boundaries.test.ts` 视同只读 |
| 踩坑后只更新 AGENTS.md                     | L1 约束容易失效                   | 推到 L3–L5（本仓库有活例：架构规则从 ADR 文字升级成了边界测试）  |
| 约束只增不减                               | 系统僵化，规则被习惯性绕过        | ADR supersede、lint 清理，触发式复审                             |
| 需求不清时让 AI "先做个版本看看"           | 歧义被固化进代码                  | 回到决策阶段澄清；代码与文档冲突时停下来问                       |
| 回退方案"到时候再说"                       | 出事时临场应对                    | `data/` 维护的校验和比对；发布前写下 revert 路径                 |

## 10. 度量：衡量这套实践本身是否有效

单人仓库不做仪表盘，看四个信号就够了：

| 信号               | 衡量什么                                    | 期望趋势         |
| ------------------ | ------------------------------------------- | ---------------- |
| **同类错误复发率** | 约束升级是否有效                            | → 0              |
| 发现阶段分布       | 错误在哪一层被抓住：决策 / 验证 / CI / 生产 | 左移，即更早发现 |
| 平均 diff 规模     | 粒度纪律                                    | 稳定在单主题以内 |
| `check` 时长       | 约束的成本                                  | 可控，不持续膨胀 |

> 不要看"AI 生成了多少代码"。生成量是成本项，不是产出项。

---

## 11. 一句话总结

> **每次变更都要小到能验证、独立到能被证伪、准备好能回退。每个被确认的错误，都要推到让它更难再次出现的那一层；每条不再有用的约束，都要被移走。**
